OpenSheaf timestamps

Extension to the OpenSheaf specification 0.1. Version 0.1 (draft), 17 November 2026. How an owner dates its signatures with RFC 3161 tokens or OpenTimestamps proofs, declares that it does so in its key log, and so resolves forks of its key log by time and confirms signatures that the core leaves unconfirmed after a key is removed. The extension is named by the URI https://opensheaf.org/opensheaf-timestamps-0.1. The text is licensed under CC BY-SA 4.0; its JSON Schema is dedicated to the public domain under CC0 1.0.
Warning. Proposal. This extension belongs to the identity proposal of the specification (owners, key logs and signatures, sections 6.5 and 13.2), on the branch proposal/identity (PR #30), not yet agreed. It is discussed in issue #55.

1. Introduction (non-normative)

In the OpenSheaf specification, every version of a line is signed by its owner, under a version of the owner's key log that lists the keys allowed to sign (sections 6.5 and 13.2 of the specification). Signatures say who made a version; they say nothing of when. Two consequences follow in the core:

  • Forks of a key log are reported, not resolved. A key removed from a key log can still sign a different version of an older key log, and so fork it; nothing in the core says which side is the owner's.

  • Signatures after a change of keys are unconfirmed. A signature naming an older key-log version counts in the core only while its key is still listed and the threshold has not been raised; otherwise the core cannot tell whether it was made before the change or after it.

Timestamps answer both, by showing that a signature existed by a date. A single researcher who never removes a key needs none of this. A journal, an institution, or anyone who rotates keys may want it, and may want it from a provider it can name. So timestamps are an extension, which an owner adopts by declaring it in its key log, and SHOULD adopt from the first version of its key log, before any key is ever removed.

2. Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY and OPTIONAL in this document are to be interpreted as described in BCP 14 (RFC 2119 and RFC 8174) when, and only when, they appear in all capitals. Terms are those of the specification: owner, key log, key-log version, signature file, witness, line, branch.

This extension follows the extension mechanism of section 4 of the specification: it never changes the meaning of what the specification defines, nor relaxes its requirements; it adds evidence, and rules that use it. A reader that does not know it reads and verifies everything by the core rules, and ignores the files and data it defines.

3. Timestamps

A timestamp of a signature file shows that the file, and so the signature and the signed message it holds, existed by a date. It proves existence, nothing more. Two kinds are defined, which an owner MAY combine:

  • RFC 3161 tokens, from a time-stamping authority (a free public one, or a qualified provider under eIDAS): <version>/signature-<k>.json.tsr, beside the signature file <version>/signature-<k>.json in the object's extension folder extensions/opensheaf-witnesses/. The file holds a DER-encoded TimeStampResp whose message imprint is the SHA-512 digest of the bytes of the signature file, requested with the authority's certificates included (-cert with openssl ts -query), so that it can be checked with openssl ts -verify without fetching them.

  • OpenTimestamps proofs of the bytes of the same signature file: <version>/signature-<k>.json.ots, beside it.

Both stamp the signature file as stored. Signature files and their timestamp files are never re-serialised or replaced once made (section 13.2 of the specification): a timestamp stamps their bytes. A timestamp MAY be supplemented later by another one of the same file (re-stamping), with another authority or with an OpenTimestamps proof, so that the evidence outlives the certificates of the first; the files are then named <version>/signature-<k>.json.<n>.tsr or .<n>.ots, <n> from 2.

A timestamp of a version's checksum file MAY also be kept, as <version>/inventory.json.sha512.tsr or .ots; it dates the version, not a signature, and is not used by the rules below.

4. The owner's declaration

An owner adopts this extension in its key log: a version of the key log holds, in its keys.json, under extensions (section 6.5 of the specification), an entry keyed by https://opensheaf.org/opensheaf-timestamps-0.1, an object with:

  • timestamps, REQUIRED: "keylog", every version of the key log is timestamped, or "all", every version of the key log and of the owner's lines is timestamped;

  • timestampAuthorities, OPTIONAL: the RFC 3161 time-stamping authorities the owner trusts, each the SHA-256 fingerprint (lowercase hexadecimal) of the authority's signing certificate or of the root certificate of its chain. Without any, only OpenTimestamps proofs meet the policy.

The declaration is part of the key-log version, so it is signed with it, and changed only by a new version. The declaration in force for any version is that of the latest version of the key log known to the reader, not that of the version a signature names: an owner that adopts the extension, tightens its policy, or changes its authorities does so for everything checked afterwards.

5. Checking a timestamp

A timestamp is valid for a signature file when:

  • for an RFC 3161 token: its message imprint is the SHA-512 digest of the file's bytes; its signing certificate, or the root of the chain it carries, has a fingerprint listed in timestampAuthorities of the declaration in force; the chain was valid at the token's genTime; and the token verifies. An authority that the owner stops trusting is removed from the list by a new key-log version: its tokens then count only if their genTime is earlier than the time of that version (section 6);

  • for an OpenTimestamps proof: it is complete, attested in a Bitcoin block; an incomplete (pending) proof counts for nothing until it is completed.

The date of a valid timestamp is the genTime of an RFC 3161 token, or the time of the Bitcoin block an OpenTimestamps proof reaches. The earliest valid timestamp of a signature file is its date.

6. The time of a version

The time of a version (of a line or of a key log) is the threshold-th earliest of the dates of its valid signature files from distinct keys naming one key-log version (section 6.5 of the specification), threshold being that key-log version's. A version with fewer dated signatures has no time.

Two times are a tie when they are equal, or when one of them is the time of a Bitcoin block and they are within two hours of each other, since block times are that uncertain. A tie is reported and decides nothing.

7. What timestamps add to the core

Under a declaration, the following rules apply in addition to those of the specification. They only confirm or resolve what the core leaves unconfirmed or unresolved; they never make valid what the core rejects.

Forks of a key log. When two valid versions of a key log with the same number fork it (section 6.5 of the specification), and the declaration in force (in the last version both branches share) is keylog or all, the branch whose first differing version has the earlier time is the owner's, and the other is reported. If neither has a time, or the times are a tie, the fork stays unresolved, as in the core.

Signatures after a change of keys. A signature naming an older key-log version vk, which the core leaves unconfirmed because a later known version removed its key or raised the threshold, counts if its date is earlier than the time of the first key-log version after vk that made that change. The same holds for a key removed and later added again, for signatures made while it was absent. Since the declaration in force is that of the latest known version, a signature naming vk also needs such a date when a version after vk adopted the extension, tightened timestamps or changed timestampAuthorities. Where the version that made the change has no time, no such signature can be confirmed.

Missing timestamps. A version that the declaration in force covers, and that has no time in a given copy, is unconfirmed there, not invalid: a host can strip timestamp files from a copy, and anyone can add one later. A declaration decides forks and confirms signatures only through timestamps that are present and valid.

8. Copies and branches

Timestamp files are witnesses, kept in the object's extension folder, and travel with the object as its signature files do (sections 6.5 and 13.2 of the specification). A copy keeps them.

A branch keeps the evidence of its parent version as content (section 10.5 of the specification): parent.signatures/ holds the parent owner's signature files of the parent version with their timestamp files beside them, and parent.keylog/ holds, for each version of the parent owner's key log, its signature files with their timestamp files. Under a declaration of the parent's owner, a branch MUST NOT be taken from a parent version whose timestamps are still pending, and its evidence carries complete proofs only, since the files of a version, once made, never change.

9. Verification

A verifier that knows this extension, in addition to the checks of section 14 of the specification:

  • validates each declaration against the schema of appendix A;

  • checks every timestamp file it finds against the signature file it stamps (section 5), reporting each as valid, invalid, pending, or from an authority not listed;

  • computes the time of each key-log version and of each version a declaration covers, and reports those without a time as unconfirmed;

  • resolves forks of key logs, and confirms signatures after changes of keys, as section 7 says, reporting ties;

  • checks the timestamp files inside parent.signatures/ and parent.keylog/ of every branch, and that none of them is pending.

10. Guidance for tools

  • Tools that create an owner SHOULD offer to adopt this extension in the first version of its key log, with timestamps at least keylog: without a declaration, a key once removed can fork the key log at any later time, and the fork cannot be resolved.

  • Tools SHOULD timestamp each signature when they make it, under a declaration, and before a version leaves its owner's hands.

  • Tools SHOULD let an owner choose its authorities, and SHOULD keep an OpenTimestamps proof beside an RFC 3161 token where an owner wants evidence that rests on no authority.

  • Tools SHOULD re-stamp RFC 3161 tokens whose certificates near their end.

11. Security considerations

  • Trust. An RFC 3161 token is immediate and checkable with common tools, but rests on the authority's clock and keys: an authority that misdates, or whose key is stolen, can date a signature falsely. Listing the authorities in the key log keeps anyone else from dating with an authority of their own. An OpenTimestamps proof rests on no authority, only on Bitcoin, but is complete only after a pending period of hours, and its date is uncertain by about as long.

  • Stripping. A host can remove timestamp files from a copy; versions then become unconfirmed, not invalid, and a copy with the files restores them.

  • Freshness. A copy that withholds later versions of a key log also withholds later declarations; the declaration in force is only as recent as the key log a reader has seen.

Appendix B. Example (non-normative)

The keys.json of a version of an owner's key log that adopts the extension, with one RFC 3161 authority (a placeholder fingerprint) and OpenTimestamps: 

{
  "format": "opensheaf-keys/0.1",
  "keys": [ "did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK",
            "did:key:z6MkpTHR8VNsBxYAAWHut2Geadd9jSwuBV8xRoAnwWsdvktH" ],
  "threshold": 1,
  "extensions": {
    "https://opensheaf.org/opensheaf-timestamps-0.1": {
      "timestamps": "keylog",
      "timestampAuthorities": [ "5b4e3f0c9d2a7e18c6f4b0a39d7e2c51f8a6b3d09e4c7a12f5b8d6e3a0c9f147" ]
    }
  }
}
