OpenSheaf: an open format for document archives and collections

Specification, version 0.1 (draft), 16 November 2026. OpenSheaf is a common, open format for archives of scholarly documents and for collections of them, built on the Oxford Common File Layout (OCFL 1.1) and the DataCite Metadata Schema (4.7). This version is experimental and may change in incompatible ways before version 1.0. The text is licensed under CC BY-SA 4.0; the JSON Schemas are dedicated to the public domain under CC0 1.0.
Warning. Draft. This version is a draft. Until version 1.0, any revision may change the format in incompatible ways, and archives and collections made now may have to be rebuilt or migrated. Do not rely on it yet for anything you cannot redo. Changes are listed in the changelog (section 17) and discussed in the issues.

1. Introduction (non-normative)

OpenSheaf is meant as a lean alternative to arXiv and to the usual publication infrastructure. Any author, group or institution can keep an archive of its documents as plain files, served as a static website, checkable by anyone, and composable with other archives:

  • Sources, not only PDFs. A deposit keeps the sources of a document with its renditions (a PDF, typically), so that the archive can be read as a website and in the authoring tool.

  • Fixed versions. Every version of every document is fixed by content hashes and never changes once deposited. Corrections are new versions, and the history can be verified from the files alone.

  • Standards, not inventions. Storage follows OCFL 1.1 and description follows DataCite 4.7. This specification only defines what these leave open: discovery of an archive, collections, provenance, withdrawal, and the profiles for external services and tools.

  • Composable collections. A collection is itself a versioned object. It can include documents and collections of other archives, pinned by digest, so that selections (by a seminar, an editorial board, a reading list) compose without copying.

  • External services are optional. Archives may deposit their documents with a DOI service such as Zenodo, publish them as a website, and keep their files in git; none of this is required by the core of the format.

Answers to common questions about the design are collected in the FAQ.

The name: a sheaf is a bundle of papers and, in mathematics, the structure in which local pieces glue into a whole, as archives kept and verified separately compose into collections. The home of the format is https://opensheaf.org/. The first OpenSheaf archive is https://mgubi.org/papers/; its values appear in the examples.

2. Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY and OPTIONAL in this document are to be interpreted as described in BCP 14 (RFC 2119 and RFC 8174) when, and only when, they appear in all capitals.

Sections marked non-normative, examples, notes and the appendices marked as such are informative. JSON means RFC 8259 JSON encoded in UTF-8 without a byte order mark. URLs are absolute unless stated otherwise; a relative URL in a JSON file is resolved against the URL of that file.

3. Terminology

  • Archive: a set of objects kept by one archive owner (a person, group or institution), with one storage root and one discovery document, identified by an archive identifier.

  • Archive identifier: a URI naming the archive independently of where it is served (section 6).

  • Base URL: the URL at which an archive is currently served, ending with /; its discovery document is at <base URL>opensheaf.json.

  • Storage root: an OCFL 1.1 storage root holding the objects of the archive.

  • Object: an OCFL object. Its kind is document or collection.

  • Document: an object holding one scholarly work (an article, notes, a thesis, a book) with its sources and renditions.

  • Collection: an object holding a list of members. A collection is a catalogue or a selection (section 10.1).

  • Catalogue: a collection that keeps objects whole, impartial about their versions: each member pins an object with all its versions, and may follow it as it grows. An archive's main collection, and the list of objects an archive mirrors, are catalogues.

  • Selection: a collection that vets particular revisions of documents (a journal, a digest, a review journal, a reading list): each member pins a revision set, and earlier or later versions are not part of the selection unless its curator adds them, by a new version of the selection.

  • Revision: a document version, as vetted by a selection, pinned by the object version that held it when it was vetted.

  • Revision set: the revisions of one document vetted by a selection (usually one; more after a correction).

  • Mirror: a copy, in an archive's storage root, of another archive's object, whole and byte for byte (section 10.4).

  • Accepted copy: a shallow branch kept by a selection, starting from a revision it vetted from another archive (section 10.5).

  • Draft: an object without a genesis record, not yet sealed; no pin may name its versions (section 6.5).

  • Sealing: the object version that adds the genesis record, made at the owner's request before a version first leaves the owner's hands (section 6.5).

  • Genesis record: the file genesis.json, written when an object is sealed and kept unchanged in all its later versions and in its branches; its seeded digest is the object's name (section 6.5).

  • Name: 52 characters of base32 from the digest of the genesis record, the same for the object in every archive, copy and branch, except a branch renamed after a clash, which takes another name of the same genesis record (section 6.5).

  • Owner: whoever decides the versions of a line (a person, group, institution or key holder), identified by a URI: none for a draft, a named owner (an archive identifier, an ORCID iD, a web address) or a keyed owner (a public key) (section 6.5).

  • Owner identifier: 52 characters of base32 from the digest of an owner's URI, which names the owner in a sheaf: URI (section 6.6).

  • Originator: the owner named in the genesis record, whose line is the origin of the name and has no parent (section 6.5).

  • Line: the history of an object as decided by one owner, identified by the pair (owner, name); its object versions form a single sequence (section 6.5).

  • Branch: a line of another owner continuing an object from one of its versions, the branch point: deep when it holds the earlier versions too, shallow when it holds only the branch point and its own versions (section 10.5).

  • Object version: an OCFL version of an object (v1, v2, …). It changes at every change of the object.

  • Document version: the version of the work, a positive integer numbered by the owner of the line (for a draft, or an archive's own documents, the archive), in object.json and datacite.json. It changes exactly when the document's own files change (section 7.3).

  • Description-only version: an object version that holds an existing document version with its files unchanged, changing only the description, the state or the notices of the object (section 7.3).

  • History: the order of a document's versions in the history of the work (section 7.3).

  • Current version: the document version to which readers are directed: the last in the history.

  • Note: a short text, a file of the content, or both, as used for change notes, notices and withdrawals (section 9).

  • Member: an entry of a collection: an object (in a catalogue) or a revision set of a document (in a selection), of any archive.

  • Pin: the pair (object version, SHA-512 digest of that version's inventory file).

  • Rendition: a file produced from the sources and deposited with them (a PDF, an EPUB).

  • Presentation: files generated from the archive for readers (web pages, indexes, HTML versions of documents). It is never authoritative.

  • Custodian: anyone who keeps copies of other archives' objects, or indexes of them, apart from those archives (section 6.6, #39).

  • Resolver: a program that finds and checks the object versions named by a sheaf: URI (section 6.6); a gateway is a resolver serving web links.

  • Witness: an independent copy or proof: a signature, a timestamp, an external deposit, a software archive snapshot.

  • Verifier: a program that checks an archive or a collection against this specification.

4. Conformance

This specification defines the following conformance classes. An archive, object or program conforms to a class if it satisfies every MUST and MUST NOT of the sections listed for it.

  • OpenSheaf archive: sections 5 to 13 and 16 (section 10 for the collections it contains).

  • OpenSheaf collection: section 10, in addition to the requirements on objects in sections 7 to 9.

  • OpenSheaf verifier: sections 12 (as a reader), 14 and 15. Tools that build presentations follow the requirements on presentations in sections 11.1, 15 and appendix C.

  • OpenSheaf resolver (proposal): section 6.6, and section 6.4 for fetching; a gateway also follows the requirements on gateways in section 6.6.

  • Profiles, optional: an archive MAY additionally conform to the Zenodo binding (appendix A), the TeXmacs profile (appendix B) and the website profile (appendix C). A conforming archive MUST state in its discovery document which profiles it follows.

  • Extensions, optional: an extension is a specification published separately from this one, named by a URI (RECOMMENDED: the https URL at which it is published), that records in object.json what this specification leaves open, so that tools aware of it can act on it (for instance relations between documents that tools must follow when they copy or verify them). An object version records the data of an extension under extensions in its object.json (section 9), keyed by the name of the extension; the discovery document SHOULD list the extensions its objects use (section 6.1). Extensions MUST NOT change the meaning of what this specification defines, nor relax its requirements: an archive is conforming, and its objects and collections are read and verified, without knowing any of its extensions. Readers ignore extensions they do not know, as they ignore unknown properties (section 12). The data of an extension is part of the object version, covered by its inventory like the rest of object.json, so pins fix it too.

The JSON files defined here (opensheaf.json, object.json, members.json, genesis.json, the index files and indexes.json of section 6.6) MUST validate against the JSON Schemas of appendix D for their declared format version.

5. Layout

An archive consists of:

  • A discovery document, opensheaf.json, at its base URL (section 6). It is REQUIRED.

  • A storage root, REQUIRED, conforming to OCFL 1.1, at a URL given by the discovery document. It MUST contain ocfl_layout.json, whose extension MUST be the storage layout named by storageLayout in the discovery document (section 6.1), one of two storage layout extensions of OCFL: 0002-flat-direct-storage-layout, so that an object with identifier <id> is at <storage root URL><id>/; or, for large archives, 0003-hash-and-id-n-tuple-storage-layout with its default parameters (digestAlgorithm sha256, tupleSize 3, numberOfTuples 3; its configuration file extensions/0003-hash-and-id-n-tuple-storage-layout/config.json, if present, MUST NOT set other values, and a parameter it omits takes its default), so that the object is at <storage root URL><t1>/<t2>/<t3>/<id>/, where <t1>, <t2> and <t3> are the first three groups of three characters of the lowercase hexadecimal SHA-256 digest of the identifier (as UTF-8). Since object identifiers are short and use only safe characters (section 6.3), the folder of an object is named by its identifier in both. Archives SHOULD use the flat-direct layout unless their size makes one folder holding every object impractical (for instance from tens of thousands of objects, or fewer in a git repository; appendix F). The layout is chosen when the archive is created: changing it keeps every pin valid, since clients compute paths from storageLayout, but moves every object and so changes every URL into the storage root (the url of a branch's parent, section 10.5, or a link in a document), so archives SHOULD NOT change it. The storage root MAY contain, as loose files allowed by OCFL, a copy of the OCFL specification and of this specification.

  • Witnesses, OPTIONAL: signatures and timestamp proofs of object versions, in each object's extension folder extensions/opensheaf-witnesses/, or under witnesses/ next to the discovery document (section 13.2).

  • Indexes, RECOMMENDED: names/, owners/ and sha512/ next to the discovery document (section 6.6, proposal).

  • Presentation files, OPTIONAL, anywhere outside the storage root, witnesses/ and the indexes (appendix C).

Because OCFL allows inside a storage root only the folders that hold objects (the objects themselves and, in the hashed layout, the folders of the hash above them) and extensions, the storage root SHOULD be a dedicated folder (by convention ocfl/), and presentation files MUST NOT be placed inside it.

All files of the discovery document, the storage root, witnesses/ and the indexes (if used) MUST be served byte for byte, as stored: no conversion of line endings or character sets, no compression that changes the bytes delivered after decoding. Archives kept in git SHOULD mark these files as binary (for instance with .gitattributes lines ocfl/** -text, opensheaf.json -text and, where used, witnesses/** -text, names/** -text, owners/** -text and sha512/** -text). Archives SHOULD be served over HTTPS and SHOULD allow cross-origin requests to these files (Access-Control-Allow-Origin: *), so that tools running in a browser can resolve members.

An archive MAY be kept in git and served by any static web server (GitHub Pages, object storage, a university server). The companion document OpenSheaf archives in git, outside this specification, says how to keep, publish and copy an archive in git without changing its bytes.

6. Discovery and identity

6.1 The discovery document

The discovery document is the JSON file opensheaf.json at the base URL of the archive. It MUST contain:

  • format: "opensheaf-archive/0.1";

  • specification: the version of this specification the archive follows, "0.1";

  • archiveId: the archive identifier (section 6.2);

  • name: a human-readable name;

  • storageRoot: the URL of the storage root, ending with / (relative URLs are allowed);

  • storageLayout: the storage layout extension of the storage root, "0002-flat-direct-storage-layout" or "0003-hash-and-id-n-tuple-storage-layout" (section 5);

  • objects: the list of all objects in the storage root, each with id, kind, head (the head object version), inventorySha512 (the SHA-512 digest of the head inventory, as written in its checksum file) and status (active or withdrawn, section 11); a mirror (section 10.4) also has mirrorOf, the archive identifier of the archive whose object it copies, which is not the archive's own; an object with a genesis record (section 6.5) also has its name and owner.

It MUST also contain profiles, the list of profiles followed, from zenodo, texmacs, website (an empty list if none). It SHOULD contain mainCollection (the identifier of the collection that lists the archive's own documents), contact (a URI) and, if its objects use extensions, extensions (their names, section 4). It MAY contain mirrors (base URLs of complete copies of the archive), tombstones (section 11.3), indexes (the indexes kept, each with the length of its prefix, section 6.6), keys (section 13.2) and feed (the URL of an Atom feed of new object versions).

The discovery document is mutable: it is rewritten whenever an object is added or changed. It is a map, not a witness: what it states about objects (objects: kinds, head versions, digests, status) MUST be verifiable from the storage root. Digests are written in lowercase hexadecimal, here and in every file defined by this specification.

6.2 Archive identifiers

An archive identifier is a URI that does not change when the archive moves. It SHOULD be a tag: URI (RFC 4151) built from a domain or e-mail address controlled by the archive owner at the time of creation and a date, for instance tag:opensheaf.org,2026:mgubi. A DOI or another persistent URI MAY be used instead. Two different archives MUST NOT use the same archive identifier.

6.3 Object identifiers

An object identifier MUST match ^[a-z0-9]+(-[a-z0-9]+)*$ and MUST be at most 64 characters long. It is the OCFL id of the object and the name of its folder in the storage root (under the folders of the hash, in the hashed layout, section 5). It MUST be unique in the archive and MUST NOT be reused, also after a takedown. Since it is permanent and appears in every URL of the object, it SHOULD be short (at most 32 characters), readable and chosen by the depositor, and SHOULD NOT be derived mechanically from the title, which may change between versions while the identifier cannot; tools importing documents propose identifiers and the depositor decides. Notwithstanding these recommendations, an archive MAY use the object's name (section 6.5), 52 characters, as its identifier, unless it keeps two objects of that name (lines of several owners). The kind of an object is given by its object.json, never by its identifier. Outside the archive, an object is named by the pair (archive identifier, object identifier) of its object.json, which a mirror keeps unchanged; with the proposal of section 6.5, its line is also named by the pair (owner, name), independently of any archive.

6.4 Resolution

To fetch an object version of a member, a client:

  • reads the discovery document at the member's archive URL (section 10.2) and fetches <storageRoot><path>/<version>/inventory.json, where <path> is the path of the object given by the storageLayout of the discovery document (section 5): <id>, or <t1>/<t2>/<t3>/<id> in the hashed layout;

  • if this fails, tries the mirrors listed in the member, then those listed in the archive's discovery document, each resolved through its own discovery document and layout;

  • if this fails, MAY use external copies: the files of an external record named in the version's object.json (a DOI record), or a software archive snapshot (a SWHID).

To fetch the parent version of a branch (section 10.5, proposal), a client fetches inventory.json at the url of parent; if this fails, or no url is given, it tries the copies it knows of the parent's archive (a member or a mirror naming the same archiveId, with its archive URL) and then external copies, as above. The url is chosen by the branch, so a copy found only there shows that the parent can be fetched, not that it is the parent's own: a verifier counts a resolved parent as confirmation (section 14) only when it reached it at a base URL of the parent's archive known independently of the branch: the archiveUrl of a member of a collection the verifier trusts (not a collection of the branch's own archive or owner, unless its user configured it), or a location configured by its user (and the mirrors listed in the discovery document found there). External copies (a DOI deposit) can attest the parent version, but do not resolve it, since they hold no inventory.

Any copy whose bytes match the pinned digest is acceptable: integrity comes from the pin, not from the place.

6.5 Names, owners and lines

Note. Proposal. This section, and the sections it changes (3 to 5, 6.1 to 6.4, 7, 8.1, 9, 10.2 to 10.6, 11.3, 13.2, 14 to 16 and appendices D to F, with the FAQ, the use cases and the companion OpenSheaf archives in git), together with section 6.6, are a proposal on the branch proposal/identity, not yet agreed. It builds on the discussions of self-certifying names (#20), decentralised holding and keys (#13), global names (#14), private and draft objects (#29) and the evidence of accepted copies (#22).

An object identifier names an object within its archive (section 6.3). An object also has a name, independent of any archive, and an owner. The pair (owner, name) identifies a line: the history of the object as decided by that owner. Copies of a line (mirrors, section 10.4) are the same line wherever they are kept; lines of other owners with the same genesis record are branches (section 10.5).

Genesis record. When an object is sealed, at its owner's request, before a version of it first leaves its owner's hands (shared privately, for instance submitted to a journal, or published; #29), its owner writes the genesis record, the JSON file genesis.json at the root of the content, with format ("opensheaf-genesis/0.1"), kind (document or collection, the kind of the object), created (the date and time, in UTC), originator (the owner of the first line, a URI) and nonce (at least 128 bits from a cryptographically secure random generator, in lowercase hexadecimal). The genesis record MUST be part of every later object version of the object and of its branches, byte for byte. It contains neither the name nor the object identifier, so that the name does not depend on itself. It MUST be written in UTF-8 without a byte order mark (section 2), and SHOULD have LF line ends; since the name is the digest of its bytes as stored, tools MUST NOT rewrite or re-serialise it, and need no canonical form to check it.

Name. The name of the object is the SHA-256 digest of the seed opensheaf-name-0 (ASCII, followed by a line feed) followed by the bytes of genesis.json, written in lowercase base32 (RFC 4648, without padding): 52 characters, a valid object identifier (section 6.3). The last character carries the last bit of the digest and, in its four remaining bits, the number k of the algorithm that made the name, from 0 to 15: algorithm k is the same with the seed opensheaf-name-<k> (k in decimal), so that algorithm 0 gives a last character a or q. Names are made by algorithm 0, except a branch named by another algorithm to avoid a clash (below); names made by different algorithms never coincide. A later version of the genesis record MAY use another hash function. Since RFC 4648 sets the four bits to zero, names are compared as strings and never decoded. Anyone holding a copy can compute it; it is unique without a registry in practice, since the record holds a random nonce; since a name is used to refer to objects, clashes are resolved where objects are created (below). object.json records it as name. An archive MAY use the name as the object identifier.

Owner. The owner of a line is a URI, recorded in object.json as owner from the first version of its line. There are three cases:

  • a draft has no owner and no genesis record yet; it receives both when it is sealed. The absence of a genesis record is what marks a draft: it is part of the content, so it travels with every copy, and no other mark is needed. An object version without a genesis record MUST NOT be named by a pin (in a collection, or as a parent). Whether a draft may be rewritten before sealing is open (#29, below);

  • a named owner is a URI that the owner asserts: the archive identifier, an ORCID iD (https://orcid.org/…), a web address the owner controls. It costs nothing, and proves no more than the archive that serves the line;

  • a keyed owner is a public key written as a URI: did:key: (the key itself) or openpgp4fpr: followed by an OpenPGP fingerprint. Every object version of a keyed line (from its first sealed version, or for a branch after the branch point) MUST be signed with that key, and the key needed to check the signatures MUST travel with the object (section 13.2), so that the line can be checked without trusting any host, also after its archive has disappeared.

A named owner MAY sign its versions with keys of its own (keys of the discovery document); its line is still identified by the named URI, and such signatures are witnesses, not proofs of ownership.

Comparing owners. Owners, originators and the owners in parent are compared as strings, exactly. Tools MUST write them in these forms: an ORCID iD as https://orcid.org/ followed by the iD, without a trailing slash; openpgp4fpr: followed by the fingerprint in lowercase hexadecimal; did:key: as defined by the did:key method (W3C CCG), multibase base58btc, for an Ed25519 key (multicodec ed25519-pub, code 0xed, written as the varint bytes 0xed 0x01); other URIs as the owner first wrote them.

One writer per line. The object versions of a line form a single sequence, each extending the one before, as OCFL objects do: an owner MUST NOT publish two different object versions with the same number for the same line, in one archive or in several. A line keeps one archive identifier and one object identifier in all its copies (a mirror keeps them unchanged, section 6.3); moving a line to another archive is open, with handing it over (below). Since every version directory keeps the inventory as of that version (section 7.1), two copies of a line can be compared from their inventories alone: two copies whose heads are vk and vm, with k not greater than m, agree when vk/inventory.json is the same file, byte for byte, in both. Two copies that do not agree are a fork of the line. For a keyed owner the signatures show that the owner made both, and the fork is its error; for a named owner it shows only that two parties wrote under the same URI, since anyone can assert it. A fork is found only by someone who sees both copies.

Depositors. An archive that accepts deposits from more than one depositor MUST bind each named owner URI of the lines it keeps (those with its own archiveId) to the depositors allowed to write under it, and MUST bind a URI only to a depositor it has checked can use it (for an ORCID iD, by an ORCID login; for a web address or an archive identifier, by control of it), so that no depositor continues another's line or opens a line under another's URI. Keyed lines need no binding, since their signatures decide, and mirrors are not bound, since they copy lines of other archives unchanged.

Origin. The line of the originator is the origin of the name, and has no parent. Every other line with the same genesis record MUST declare its parent (section 10.5); a line of another owner that declares none is not a valid line of the name.

Sealing and transfer. The object version that seals a draft adds the genesis record and makes its owner the first writer. The owner seals an object before first sharing or publishing a version of it, and tools SHOULD seal only at the owner's request, not as a side effect. A draft MAY be kept in an archive (served only to its owner, or listed in a public discovery document as work not yet shared, on which nothing may rely, #29), but cannot be pinned: a catalogue that follows it (section 10.2) pins it only once it is sealed. Versions made before sealing stay in the object's history, fixed by every later pin like any earlier version, but belong to no line and cannot be named by a pin or vetted (whether sealing may instead rewrite them is open, below). This proposal does not hand lines over (an open question, below): when another owner continues the work (an author leaving an institution's repository, when the line is the institution's; a journal handing a report to its referee; a line the author owns as originator is not branched by the author but moved, an open question below), the new owner makes a deep branch (section 10.5), and the previous owner MAY add a notice to its own line pointing to the branch.

Clashes. A name is used to refer to objects, so the format does not assume that two works never share one: in an archive, an object is identified by its line, and no two objects of an archive have the same owner and name (section 14). A clash can arise only when an object is created or deposited in an archive, and is resolved there, against the archive and the confirmed lines of the same owner elsewhere:

  • when sealing, a tool checks the line (owner, name) against the archive and, if it is taken, draws a new nonce, so that the originator's line is always named by algorithm 0; an object sealed outside the archive's storage root and shared before its deposit can still meet a taken line when it is deposited (after a reused genesis record or a collision, or when the archive already holds a copy or a tombstone of the same line), and is then refused: when the archive holds a copy, the line stays with the archive that keeps it (moving a line is open, below); otherwise its owner seals it anew;

  • a branch is never owned by the originator, whose line is the origin and has no parent: how the originator takes in another line's work is open (below); a tool refuses such a branch;

  • a branch is named by parent.name, unless its line (its owner, that name) is taken by another object, in its archive (any object there, or a tombstone) or among the other lines of its owner that the tool knows elsewhere and that are confirmed (section 6.6: reached through the archive named by their archiveId, known independently, or signed by a keyed owner); a line known elsewhere only from index entries, without a confirmed copy, is reported and never causes a rename; if that object is the owner's own branch (one the owner made: for a keyed owner, its signatures hold; for a named owner, the archive that keeps it accepts the move under the same authority it requires for any new version of that line; any other object counts as another object; a mirror of the owner's own branch counts as that branch) of the same parent line and the new branch point is later in the parent line's history than that branch's current branch point, the owner moves its branch point instead (section 10.5), in the archive that keeps that branch, and a mirror of it is then brought up to date; a tool that cannot do so renames the new branch as below; otherwise (another genesis record, a mirror of anything else, another parent line, an earlier or equal branch point) the branch is named by the smallest algorithm number greater than that of parent.name whose name, over the same genesis record, gives a line free in the archive and among the owner's known confirmed lines; parent keeps the parent's name; if no number up to 15 is free, the branch is refused. An accepted copy of another selection is not renamed: owners differ between selections (section 10.5);

  • a mirror whose line is taken cannot be kept there;

  • a line stays taken after a takedown (section 11.3: the tombstone keeps the name and the owner identifier), like the object identifier, so that a removed line and a new one never share a URI in that archive.

Other owners' lines are different lines and never clash. A renamed branch is always written with its owner part (section 6.6), since a URI without an owner part names the originator's line, which is named by algorithm 0; a resolver given a renamed name without an owner part finds no originator's line, and reports it, pointing to the search for the work. Lines of one owner in archives the tool does not know may still duplicate each other; they are forks of the line, found by resolvers (section 6.6).

Refusals. One genesis record names one work, and one owner identifier one owner. Every line records, in sealed of its object.json (section 9), the version that sealed the work: the archiveId, objectId and objectVersion of the originator's sealing version, which every branch copies unchanged from its parent. When an object is created or deposited, an archive refuses an object whose genesis record is that of an object it holds, or one of whose 16 names is the name of a tombstone it holds (section 11.3), but whose sealed differs from that object's or tombstone's (a genesis record reused for another work: its owner seals the other work anew); and an object whose owner (at its head; for a mirror, the mirrored line's) has the owner identifier of another owner at the heads of the archive (another URI): it is kept only under another owner URI, and a mirror is then refused. A tool MUST NOT copy a genesis record into an object that is not a mirror or a branch of the work it was written for, nor reuse a nonce. What an archive cannot see (a clash with an object or an owner of another archive) is found by resolvers: the search for a work groups lines by sealed and lists different groups as different works, and owner identifiers are compared through owners/ (section 6.6).

Existing objects. This draft assumes that every sealed object has a genesis record: archives made under earlier drafts are rebuilt, as the warning at the head of this specification allows before version 1.0.

Open questions.

  • Registering the scheme sheaf with IANA, as a provisional scheme (RFC 7595), since section 6.6 uses it in place of the tag: or ARK form chosen in #14 (#36); whether the pair (archive identifier, object identifier) keeps a URI form of its own beside sheaf: URIs; the form of archive identifiers (tag: or ARK) (#14), or names made as object names are, from a genesis record of the archive, with an owner (#52).

  • Who keeps indexes of many archives, so that an object can be found once its archive has gone, how resolvers find them, and whether the project runs a shared resolver of sheaf: URIs, a gateway (section 6.6): at https://opensheaf.org/sheaf:…, as written provisionally, or on a domain used only for resolution, such as https://sheaf.pub/, without sheaf: in the path (#13, #20, #35).

  • How co-authors own a line: one owner, a group key, several controllers as #20 proposes, or a branch each; and how the originator takes in another line's work (a co-author's, a journal's corrections), since its line has no parent and it does not branch its own work.

  • Lines of one owner duplicated in archives that do not know of each other (two branches of one co-author, accepted copies of one journal in two archives): forks that only resolvers see.

  • The numbering of document versions on branches after the branch point (section 10.5), which /v<n> in a sheaf: URI follows (section 6.6).

  • Whether a line may be handed over to another owner, instead of being continued by a deep branch, or moved to another archive, under another archive identifier.

  • Moving a branch point when the branch has files of its own (the files of its notices, of a withdrawal, of its version of record): the moving version should probably be a merge keeping both, the new parent version's files and the branch's own, with evidence that tells them apart (section 10.5).

  • Keys: whether lines should require them (#20 proposes so); loss, compromise and rotation (did:key cannot rotate, while did:web or did:webvh can); several keys per line, including a recovery key; tying a key to an identity such as an ORCID iD (#13, #41).

  • Whether a draft may be rewritten before it is sealed, against the rule that versions are fixed, and whether tools MUST seal only at the owner's request (#29).

  • Holding and copying among custodians, which this proposal leaves to #39: copies kept apart from the storage root, mirrors as locations, mirrors made by agreement, and statements of custodians; #52 proposes that a site keep one storage root per archive it holds, writing only to the one whose owner authorises it, which would remove the refusals of mirrors in section 10.4 and under Clashes above.

  • Takedowns: a branch keeps the parent version after the parent is taken down, and mirrors, indexes kept by others and gateways may go on serving a taken-down object (#33).

  • A deep branch whose parent's object identifier is already taken in the branch's archive.

  • Whether aliases (a new genesis record that wraps the old one) are needed, if refusing reused genesis records and colliding owner identifiers at creation (section 6.5) proves too strict, and whether a sheaf: URI may write the owner itself instead of its identifier (#44).

  • The field names: name also names the archive, in the discovery document.

6.6 Names as URIs and finding objects

Note. Proposal. This section is part of the proposal of section 6.5 (branch proposal/identity): writing lines, versions and pins as URIs, and finding objects by name (#14, #20). It replaces the decision recorded in #14 (global names as tag: or ARK URIs built from the archive identifier, with sheaf: kept in reserve): a line now has a name independent of any archive, and sheaf: URIs write it; archive identifiers stay as section 6.2 says.

Owner identifier. The owner identifier of an owner is computed as a name by algorithm 0 (section 6.5), over its URI as recorded (in the canonical form of section 6.5, where one is defined), encoded in UTF-8 without a line end, instead of genesis.json: 52 characters. It names an owner inside a URI, where the owner's own URI, which holds : and /, cannot be written. genesis.json, object.json, parent and the members of collections record the owner's URI, never its identifier; indexes record both (below), and tombstones the identifier, and the URI unless a takedown erases it (section 11.3).

**The sheaf URI.** A line, a document version of a line, one object version, or the object as a whole, is written as a URI of the scheme sheaf: 

sheaf:<name>                            the line of the originator
sheaf:<name>:<owner id>                 the line of that owner
sheaf:<name>:*                          the object as a whole, all its lines
sheaf:<name>/v<n>                       document version n of the originator's line
sheaf:<name>:<owner id>/v<n>            document version n of that owner's line
sheaf:<name>[:<owner id>]/v<n>?sha512=<digest>   one object version holding it

The parts are, in this order: sheaf: and the name; optionally : and an owner identifier, or :*, which names all the lines and takes no document version and no sha512 (the owner part is : and an owner identifier; :* is not an owner part); optionally /v and a document version, a positive integer without leading zeros; optionally ? and a query of parameters key=value joined by &, among them at most one sha512, only after a document version, whose value is the SHA-512 digest of an inventory file, 128 lowercase hexadecimal digits, as in a pin (section 10.2), and at most one at, after sha512 if both are present (below). A resolver ignores parameters it does not know; no part other than the value of at is percent-encoded; this proposal defines no fragment. The scheme, the name, the owner identifier, v, the digest and the parameter names are lowercase, and a resolver MAY fold uppercase letters in them; the value of at is case-sensitive.

  • The owner. Without an owner part, a URI names the line of the originator, the owner named by originator in the genesis record, which every copy of the object and of its branches carries. If a resolver finds several genesis records under one name (with the same originator or not), the URI is ambiguous: it lists them with their originators and does not choose. It does not mean the latest line or the most authoritative one: the versions of any other line, such as a journal's or a co-author's, are written with their owner, and if the originator stops and another owner continues the work in a deep branch, the URI still names the originator's line. sheaf:<name>:* names the object as a whole, with all its lines: a resolver shows the lines it knows that pass the checks below, each marked confirmed or unconfirmed. A resolver rejects :* with a document version or sha512, since every line has its own document versions (section 10.5); at is allowed with it.

  • The version. /v<n> is a document version of the line (section 7.3, also on a branch), not an OCFL object version. It names only object versions of the line: sealed versions (with a genesis record) whose object.json has the line's owner. The versions of a deep branch up to its branch point belong to the lines they were copied from (the parent's, or for a deep branch of a deep branch an earlier one's), and are named with those lines' owners; a document version held only by versions made before sealing (section 6.5) belongs to no line and has no sheaf: URI. On a deep branch, a document version held only by its copied versions names nothing on the branch's line: a resolver points to the URI of the line that holds it. Several object versions of the line may hold document version n: without a digest, the URI names the one listed for n in the history of the line's head, or, without history, the last object version of the line holding n (section 7.3). What it names can then change as the line grows, by a description or a notice, and copies with different heads may answer differently: a resolver uses the latest head among the confirmed copies that agree (section 6.5, and below), and reports a later head found only in unconfirmed copies as an unconfirmed extension, without using it; with no confirmed copy, it uses the latest head among the unconfirmed copies that agree, and reports the result as unconfirmed; if some unconfirmed copies disagree with the others, it lists them all and does not choose.

  • The pin. With a digest, the URI names exactly the object version whose inventory file has that digest. A resolver MUST check that digest, and that the version holds a genesis record whose name, by the algorithm of the name's last character, is the name, has the URI's name as name and the line's owner as owner in its object.json (the owner part, or the originator), and holds document version n; it reports a mismatch as section 14 does. Citations of a fixed version SHOULD carry the digest.

  • The hint. at names an archive where a copy is expected, where a resolver looks first: its value is the archive's base URL, an https URL ending with /, percent-encoded in full (every character outside the unreserved characters of RFC 3986 is encoded, as encodeURIComponent does) and decoded once: sheaf:<name>/v3?sha512=<digest>&at=https%3A%2F%2Fauthors.example.org%2F. It is not part of the identity.

  • Equality. The canonical form of a sheaf: URI has complete parts, lowercase where the case is folded, and, for :*, the name made by algorithm 0, since all the names of a genesis record name the same work; it has no owner part when the owner is the originator (read from the genesis record, which any copy carries and the name certifies, section 6.5, so that deciding equality may need one copy of genesis.json), and no at and no unknown parameters. Two URIs name the same thing when their canonical forms are equal, byte for byte, and files that record a sheaf: URI (for instance among the relations of datacite.json) record its canonical form.

Checks and confirmation. A resolver checks every copy it finds: the name is a name of its genesis.json, by the algorithm of its last character, the name and owner in object.json are the line's, and, with a digest, the rest of the checks of a pin. A copy that passes them is the object version named by a URI with a digest, wherever it was found, since the pin fixes it. Without a digest, a copy shows only that someone published versions under that owner and name, which a named owner cannot prevent (section 6.5): a resolver MUST report such a copy as confirmed only when it reached it at a base URL of the archive that keeps the line (the archive named by archiveId in the copy's object.json), known independently of the URI and of indexes kept by others, as section 6.4 says, or when the owner is keyed and its signatures hold; confirmation reads archiveId from the copy's own object.json, never from an index entry. This confirms the archive that keeps the line, not the person or body its owner names, which owner proofs would show (#41); it MUST report every other copy (one found through at, or through an index kept by a custodian) as unconfirmed, with where it was found. When confirmed copies of a line disagree (for a keyed owner, copies whose signatures hold), they are a fork (section 6.5): the resolver reports it and does not choose. Confirmed copies of the same named owner and name whose archiveId differ are a conflict about which archive keeps the line, since a line has one archive identifier (section 6.5): the resolver reports it with the archives, and does not choose. An unconfirmed copy that disagrees with a confirmed one is reported as a warning, and does not stop the resolution.

Searching for a work. A work is its genesis record, and its lines may be named by any of the 16 names the record gives (section 6.5: a branch is renamed after a clash). To find every line of a work (for sheaf:<name>:*, or a search by work), a resolver: obtains the genesis record (from any entry or copy found under the name, checked against it); computes its 16 names, by every algorithm; looks each of them up in the indexes it knows; and keeps only the entries whose genesis record is, byte for byte, the one it obtained, discarding the others as collisions (removed entries without a genesis record are listed apart, as removed lines of those names; removed entries that kept it are grouped by the sealed of the index, there being no copy, and marked removed); it groups the lines it keeps by their sealed, read from the copies (object.json), not from indexes kept by others, and lists different groups as different works (a genesis record reused in two archives), each marked confirmed or unconfirmed like lines, without choosing. The comparison is of bytes, so it does not rely on any hash being free of collisions. Resolving a line needs no search: sheaf:<name> names the originator's line, always named by algorithm 0 (a clash when sealing draws a new nonce), and sheaf:<name>:<owner id> names exactly that line.

Short forms. For people reading and typing them, the name and the owner identifier MAY be shortened to a prefix of at least 8 characters: sheaf:2kukpn74/v3, sheaf:2kukpn74:xx2gb5hz/v3. A part of 52 characters is complete; a shorter one is a prefix. A short name with :* (sheaf:2kukpn74:*) expands among names, whatever their owners, and is ambiguous when names of several genesis records match; once expanded, the work is searched for as above. A resolver expands a short form among the lines it knows of (from the indexes below, the archives and collections it reads, and its user's configuration), counting only the lines whose copies pass the checks above:

  • the candidates are the lines whose name starts with the name part and whose owner identifier starts with the owner part; without an owner part, the lines of the originators. Each is confirmed or unconfirmed, as above: confirmed when a copy was reached through the archive that keeps the line, at a location known independently, or is signed by its keyed owner;

  • if there are confirmed candidates, all of the same owner and, for a named owner, kept by the same archive (the same archiveId), the short form names the first of them in that owner's order: the line whose first object version of that owner (for the originator, the version that sealed it; for a shallow branch, its first version; for a deep branch, its first version after the branch point) has the earliest created in its inventory, compared as instants. The unconfirmed candidates MUST NOT win: the resolver shows them beside its answer, as warnings;

  • if there is no confirmed candidate and exactly one unconfirmed one, the short form names it, and the resolver reports it as unconfirmed;

  • otherwise (confirmed candidates of different owners, or of one named owner in different archives, two with the same created, or several unconfirmed candidates and no confirmed one), the short form is ambiguous: the resolver MUST NOT choose one, and lists the candidates with their full forms, their originators and the archives that keep them.

The order of an owner's lines is trusted only within one archive that keeps them, or under the owner's key. Anyone can write a line under a named owner's URI, with any created, and search for a name with a given prefix (8 characters are 40 bits); such a line is unconfirmed, unless its maker also runs an archive the resolver knows, and then it is confirmed in another archive than the owner's lines, so the short form becomes ambiguous: it is seen, and cannot take the short form over. Another owner, confirmed in an archive of its own, can likewise at most make a short form ambiguous. A resolver knows only the lines it has seen, and confirms only those whose archives it knows, so two resolvers may expand a short form differently, and a short form that is unique today may become ambiguous later, while a full form never changes. Short forms are therefore for people (text, citations, a lookup typed by hand): pins, parent, members.json and every other file defined by this specification MUST use complete parts, never prefixes, a resolver SHOULD show the full form of what it resolved, and landing pages and citation metadata SHOULD give the full form, and MAY add a short one. A short form printed or kept where it cannot be corrected (a paper, a slide) SHOULD have at least 16 characters in each part (80 bits), which cannot be searched for.

Indexes. To find objects by name, by owner or by inventory digest without knowing their archive, an archive SHOULD keep three indexes of its own objects next to its discovery document, declared there in indexes (section 6.1), and a custodian or a resolver MAY keep the same files for the objects of many archives, at a base URL of its own, declared in <base URL>indexes.json:

  • names/<p>.json, where <p> is the first characters of a name: the objects whose names start with them, each entry with name, originator (from the genesis record), owner, ownerId and objectId, and genesis, the exact text of its genesis.json, the string whose UTF-8 encoding is exactly the bytes of the file, so that a work can be searched for, and collisions removed, from the indexes alone (above); and sealed, as in object.json;

  • owners/<p>.json, where <p> is the first characters of an owner identifier: the owners whose identifiers start with them, each entry with ownerId, owner and names, the names of that owner's objects in the storage root, so that the lines of an owner can be listed (in an index kept for several archives, one entry for each owner and archive); a takedown removes the name, and the entry once it lists none;

  • sha512/<p>.json, where <p> is the first hexadecimal digits of an inventory digest: the sealed object versions whose inventories have digests starting with them, each entry with inventorySha512, objectId and version (the object version), and status, the object's.

The length of <p> is declared for each index, from 2 to 4 characters: 2 suits a small archive, while an archive of millions of versions declares 4, so that each file stays small. Each index file is a JSON object with format ("opensheaf-index/0.1"), index (names, owners or sha512, the folder it is in) and entries, every entry starting with the file's <p>; the declaration (in indexes of the discovery document, or in indexes.json, a JSON object with format and indexes) maps each index kept to the length of its <p>. An index kept for several archives adds to each entry archiveId and archiveUrl: the archive serving that copy and its base URL (for a mirror, the mirroring archive). An archive's indexes list every object of its storage root with a genesis record and every sealed version of it, each entry of names/ and sha512/ with status (active or withdrawn); a tombstoned object keeps its entries with status removed, so that a resolver can report it as section 11.3 asks; a removed entry of names/ keeps name, ownerId, objectId, status and sealed, and MAY drop owner, originator and genesis, so that a takedown can erase them (section 16). A file with no entries is omitted, so that, where the indexes are declared, a missing file means no entry. A resolver looks up a URI in names/ at the archives and indexes it knows, starting from at, keeping the entries whose ownerId matches the owner part, or, without an owner part, those whose owner is their originator (for a removed entry without them, whose ownerId is the owner identifier of the originator read from any copy of the genesis record; when no copy of the genesis record is found, it is reported as a removed line of that name, owner unknown), or, for :*, every entry found by the search for the work (above), each line checked and confirmed separately, then reads the history of the object it finds, at the path given by the layout of that archive's discovery document (section 6.4); it looks up a pin in sha512/, and an owner in owners/ (two different owner URIs under one owner identifier are a collision: the resolver lists them and does not choose); at an archive that keeps no indexes, it MAY read objects of the discovery document instead, which gives each object's name and owner, and fetches genesis.json and object.json from the objects for the search. Like the discovery document, indexes are maps, not witnesses: they are rewritten when objects change, and a resolver checks what it finds as above.

Gateways. Browsers do not resolve sheaf: URIs. A gateway is a web service that does it for them: it serves a URI at its base URL followed by the URI, unchanged, for instance https://opensheaf.org/sheaf:2kukpn74/v3?sha512=c07a…, so that an absolute link and its URI are turned into each other by adding or removing the base URL (a relative link starting with sheaf: is read as a sheaf: URI, so gateway links are written in full). A gateway is a resolver like any other, and:

  • it MUST answer with a real HTTP status: a page (200) showing what it resolved, or a temporary redirect (302, 303 or 307) to a copy; it MUST NOT redirect permanently (301 or 308), since copies move and are taken down, and it MAY cache its own result for a URI with a digest, but not for one without; it MUST redirect only to a copy at a base URL of the archive that keeps the line, confirmed as above (section 6.4, the mirrors listed in that archive's own discovery document included), never to a location given only by at or by an index kept by others, and otherwise answers with a page that links to the copy and marks it unconfirmed; sheaf:<name>:* shows the lines it knows;

  • it MUST show whether what it resolved is confirmed or unconfirmed, and where it was found, and treats a copy found only through at, for a URI without a digest, as unconfirmed;

  • it MUST NOT serve the files of an archive from its own origin, but redirects or links to the archive (section 15);

  • when it fetches on behalf of its users, it MUST fetch only https URLs at public addresses, with limits on size and time.

Whether the project runs a gateway, on which domain, and whether a domain used only for resolution (such as sheaf.pub) drops sheaf: from the path, as https://doi.org/ drops doi:, is still to be decided (section 6.5, #35).

7. Objects

7.1 Common rules

Every object MUST be a valid OCFL 1.1 object. Its inventories MUST use sha512 as digest algorithm. Every object version MUST contain, in its content, the files object.json and datacite.json at the top level, and, from the version that seals the object, genesis.json (section 6.5); every version of a shallow branch, and every version of a branch from the version that moves its branch point, also holds parent.inventory.json and parent.object.json (section 10.5), unchanged until the branch point moves again; a deep branch of such a branch copies them with the versions it copies, but its own versions do not hold them until its own branch point moves. These are the identity files of the object; they are not files of the document's own (section 7.3), and the names genesis.json, parent.inventory.json and parent.object.json are reserved for them at the top level of the content. Every version directory MUST contain a copy of the inventory as of that version, with its checksum file (OCFL makes this a recommendation; OpenSheaf requires it, so that each version can be pinned and fetched on its own). Version directories MUST NOT be zero-padded (v1, v2, …, not v001), which OCFL allows. OCFL recommends that object identifiers be URIs; OpenSheaf identifiers are short names (section 6.3), so OCFL validators may warn about them.

Each version in the inventory MUST have a user with a name, and SHOULD have an address (an ORCID iD, a mailto: URI or another URI identifying the depositor), and MUST have a message describing the change. The inventory is the record of deposits: the created date and the user of an object version are when and by whom it was deposited, and the deposit of a document version is that of the first object version holding it. They are not repeated in object.json.

Logical paths MUST be encoded in UTF-8 in Unicode normalisation form C, MUST NOT begin with /, and MUST NOT contain . or .. segments.

7.2 Documents

A document version contains, at the top level of its content unless a profile says otherwise:

  • the sources: the main source and every file needed to produce the renditions that is not part of the toolchain (images, bibliography databases, local style files). The main source is named in object.json. Sources SHOULD be flat (no sub-folders) when possible. When the sources of a version are not available (for instance a version imported from a service that keeps only its PDF), the version has none, and object.json says so (section 9);

  • the renditions, OPTIONAL but RECOMMENDED: at least a PDF for documents meant to be read and cited, named in object.json;

  • the files of notes, if any (the change note, notices, a withdrawal; section 9), named in object.json;

  • datacite.json (section 8) and object.json (section 9), and the identity files of section 7.1 (genesis.json, and, where section 7.1 requires them, parent.inventory.json and parent.object.json).

HTML versions and other presentation files SHOULD NOT be deposited, since they depend on the presentation and are regenerated when it improves.

7.3 Document versions

Numbering. Document versions are numbered by the owner of the line (for an archive's own documents, the archive), from 1, without gaps, independently of any external numbering: a work whose versions 1, 3 and 4 are available on arXiv has document versions 1, 2 and 3. A branch (section 10.5) starts from the document version of its first branch point (for a deep branch, an own version that adds no files of the document's own keeps the number it holds; its first own version that adds files of the document's own takes the number after the highest document version in the object, the copied versions included, and goes last in history, so that the branch's own work is its current version, and its later versions follow the rules of this section; a branch does not complete the versions it copies from its parent), and continues without gaps from it (provisionally: option (a) of the open question of section 10.5); an object version that moves the branch point is the branch's next document version (on a deep branch, the number after the highest in the object), and parent keeps the parent's own number.

Identity versions. An object version that seals an existing draft without adding files of the document's own adds only identity files (section 7.1), which are not files of the document's own: it keeps the document version it holds, and is otherwise treated as a description-only version. An object sealed by a version that also adds files of its own (for instance an object sealed at its first version) takes a new document version, as any new version does. External labels (arXiv's v3) are recorded in external (section 9), and presentations SHOULD show them with the document version.

New versions. A new document version number is assigned exactly when files of the document's own (sources, renditions, change note) that were not deposited before are added, except when a version without sources is completed (below). An object version holding the same sources, renditions and change note as an earlier document version keeps its number.

Description-only versions. A description-only version holds an existing document version, with its files unchanged, and changes only its description (datacite.json, such as a DOI, a stage or a link to the published article), the state of the object or its notices. It MAY hold any document version, not only the current one, so that an earlier version can be described after later versions exist; tools otherwise hold the current version. If the object has history, its entry for that document version becomes the new object version.

Completion. A document version recorded without sources (section 9, sourcesMissing) MAY be completed later, keeping its number: the completing object version adds the sources, and MAY add renditions produced from them (for instance a PDF typeset from the added sources, beside the one received), but changes or removes no file of the version; until the sources are complete it keeps sourcesMissing and names no main source; the object version that completes them names the main source and removes sourcesMissing, after which the version is fixed like any other.

Other versions. A version that was not public at the time, such as the manuscript submitted to a journal, deposited later, is a document version like any other. A version published by someone else, such as the journal's version of record, is not a document version of the author's object: it is linked by a relation (section 8.1). Conversely, a shallow branch holds versions of its parent's owner only at its branch points, while a deep branch also holds the earlier ones, unchanged (section 10.5).

History. The order of the document versions in the history of the work is the order of their numbers, unless object.json has history (section 9): the list, in the order of the work, of the last object version holding each document version. The last object version is used because it carries the most complete description of that document version (a DOI added later, a corrected stage). An object version that deposits a document version out of order (an earlier version found later) MUST write history, and once an object version has history, every later object version MUST have it. A version whose place in the history is unknown goes just before the current version, and its object.json SHOULD say so in its change note. The history is read from the head version; earlier object versions keep the history as it was known when they were made.

Current version. The current version of a document is the last entry of the history of its head version (without history: the highest document version). The head may hold another document version, after an earlier version is deposited out of order or described by a description-only version; the current version stays where it was. Landing pages, indexes and citations use the current version, not the head; selections vet revisions explicitly (section 10.2).

Notices. A notice about a document version (for instance that a theorem of version 2 is wrong as stated, and is corrected in version 3) is written after that version, which cannot change. Notices are added to notices in object.json (section 9) by description-only versions. A notice present in an object version is present, unchanged, in every later object version; a notice is corrected or withdrawn by a later notice that says so. Presentations showing a document version SHOULD show the current notices about it.

Dates never order document versions and never decide the current version (section 8).

7.4 Collections

A collection version contains datacite.json, object.json, members.json (section 10), which states whether the collection is a catalogue or a selection, and the identity files of section 7.1. Its object.json declares kind collection; its document version counts the changes of the member list, and it has none of the fields specific to documents (mainSource, sourceFormat, sourcesMissing, renditions, toolchain, changes, stage, history, notices).

8. Description: datacite.json

Every object version MUST contain datacite.json, a JSON object with the DataCite 4.7 properties in the form of the attributes of a DOI in the DataCite REST API. It is the authoritative description of the object version. It MUST contain:

  • titles, creators (with name, and nameType; personal names SHOULD also have givenName and familyName), publicationYear, types (with resourceTypeGeneral), version (the document version, as a decimal string without leading zeros, such as "3"), and publisher.

It SHOULD contain:

  • descriptions with a descriptionType Abstract, as plain text with mathematics as below;

  • subjects with a subjectScheme (any scheme; MSC2020 is common in mathematics);

  • dates, as below;

  • rightsList: for a licence with an SPDX identifier, that identifier in lower case and the licence URL; for a licence without one, its name in rights and the URL identifying it in rightsUri (for arXiv's default licence, http://arxiv.org/licenses/nonexclusive-distrib/1.0/), which MUST then be present, so that archives record the same licence the same way; or a statement such as "All rights reserved", without URL;

  • language, formats (the media types of the sources and renditions) and sizes;

  • identifiers of creators (ORCID) and of affiliations (ROR), where they exist;

  • relatedIdentifiers (section 8.1).

publisher is the archive's name, or the external service registering a DOI for the version (appendix A). publisher and affiliation SHOULD be written as objects (with name and, where available, an identifier); readers MUST also accept plain strings.

doi and url are OPTIONAL: they are present when the version has a DOI. types gives the kind of content: resourceTypeGeneral from DataCite's list (Preprint, JournalArticle, Book, Dissertation, Report, Text, Dataset, Software, Audiovisual, Presentation (slides, since DataCite 4.7) and so on, and Collection for collections), with resourceType for detail (for instance "Lecture notes"). An author's versions of a work not published elsewhere are Preprint, also the accepted manuscript; the stage of a version is given by stage in object.json (section 9).

Dates. Dates are information for readers and services: they never order document versions (section 7.3). Each date type has one meaning:

  • Issued: the first public appearance of the work, anywhere; the same in every version. RECOMMENDED for documents; tools importing works published elsewhere SHOULD set it.

  • Available: when this document version first became public, anywhere: for a version imported from another service, its date there; for a version first made public by this archive, the date of its deposit (section 7.1). SHOULD be present.

  • Updated: the date of the latest description-only version holding this document version; absent when the document version has had none.

  • Created (when a version was written, for a version not public at the time), Submitted and Accepted (journal milestones), OPTIONAL.

  • Withdrawn: the date of a withdrawal, equal to withdrawal.date in object.json (section 11.1).

Mathematics in titles and abstracts. Titles and abstracts are plain text in which mathematics MAY be written in LaTeX between single dollar signs ($\Phi^4_3$); a literal dollar sign is written \$. The LaTeX SHOULD use only the mathematical commands of LaTeX with the amsmath and amssymb packages, which common renderers (MathJax, KaTeX) display without the document's preamble; presentations render it, and readers that do not are left with readable LaTeX. Tools importing titles and abstracts from elsewhere SHOULD replace the authors' own macros (such as \R or \be) with standard LaTeX when their definitions are known, for instance from the preamble of the imported sources, and otherwise keep them unchanged; they MUST NOT invent definitions.

Dates MAY be approximate, as DataCite allows (2019, 2019-03, a range 2018/2019), with dateInformation explaining them (for instance "from file timestamps"); unknown dates are omitted.

8.1 Relations

  • A document version with a DOI SHOULD have IsVersionOf the concept DOI of the document, and IsNewVersionOf the DOI of the document version before it in the history (section 7.3), if that version has a DOI. Relations state what was known when a version was described; after a version is deposited out of order, the relation of the version that follows it MAY be corrected by a description-only version.

  • The same work published elsewhere SHOULD be linked with IsIdenticalTo (same content, for instance an arXiv version) or IsVariantFormOf (different content or form).

  • A preprint SHOULD be linked to its later published article with IsVersionOf the article's DOI, as DataCite recommends; consumers distinguish this relation from the concept DOI by its target. It is added by a description-only version.

  • The sources MAY be linked to a software archive snapshot (relatedIdentifierType SWHID).

  • (Proposal) A sheaf: URI (section 6.6) is recorded with relatedIdentifierType URL, in its canonical form, since DataCite has no type for it; this is provisional, until the scheme is registered (#36).

  • A collection version MUST have HasPart for each member (each revision, in a selection) that has a version DOI, pointing to that version DOI. Members without a DOI are listed only in members.json.

  • A document MUST NOT state the collections that include it: membership is stated only by collections, so that including a document in any collection never changes the document.

9. The object: object.json

Every object version MUST contain object.json, OpenSheaf's record of the object as of that version: its identity, the structure of its content, its versions and its state. It MUST contain:

  • format: "opensheaf-object/0.1";

  • specification: "0.1";

  • kind: document or collection;

  • archiveId, the identifier of the archive that keeps the line, which MUST be the archive's own except in a mirror (the mirrored archive's, section 10.4) and in the versions a deep branch copies (those of the lines they belong to), and objectId, the OCFL id of the object;

  • documentVersion: a positive integer, equal to the version of datacite.json;

  • status: active or withdrawn (section 11).

From the first version of its line (section 6.5: the version that seals it, or for a branch the first version after the branch point), an object MUST also contain name, owner and sealed (the originator's sealing version, with archiveId, objectId and objectVersion, section 6.5), and a branch parent (section 10.5). The versions of a deep branch up to its branch point are those of the lines it copies (the parent's, or earlier ones'), and their object.json files name those lines' archives and owners.

A document MUST also have mainSource (a logical path) and sourceFormat (the media type of the main source), and SHOULD have renditions (a list of objects with path, a logical path, and mediaType) and toolchain (a list of tools with name, version and, optionally, packages), enough to reproduce the renditions. A document version whose sources are not available instead has sourcesMissing, a note (see below) saying why (for instance "arXiv keeps only the PDF of this version"), no mainSource and sourceFormat, and at least one rendition; a rendition is never presented as a source.

A note is an object with text (a short plain text), or path and mediaType (a file of the content of the same object version), or both: the text serves feeds, indexes and external services, the file holds the full statement (with mathematics, or as a PDF). Files of notes are covered by the inventory like every file of the content.

A document MAY contain:

  • changes: a note saying what changed in this document version, written and deposited with it (like arXiv's comments). It is part of the document version (section 7.3);

  • stage: the stage of this document version, an object with scheme and value. For articles the RECOMMENDED scheme is NISO-JAV, the NISO Journal Article Versions: AO (author's original), SMUR (submitted manuscript under review), AM (accepted manuscript), P (proof), VoR (version of record), CVoR (corrected version of record), EVoR (enhanced version of record). Other kinds of content use other schemes (editions, software releases), named by the archive. A description-only version MAY add or correct it;

  • history: the list of object versions giving the order of the document versions (section 7.3);

  • notices: a list of notices (section 7.3), each a note with the documentVersion it is about and a date.

Any object MAY contain:

  • licence: a note with the full text or terms of the licence of the content, kept in the package (useful for licences without an SPDX identifier); rightsList in datacite.json remains the description for readers and services;

  • agreement: a minimal record that the authors agreed to the deposit and to the licence: by (the names of those who agreed, names only), date, and method (how, for instance "by e-mail"), all three required. It MUST NOT contain e-mail addresses, correspondence or signatures of persons;

  • external: the external records of this version, each with its role (required): deposit for a deposit of the version made by the archive (appendix A), source for the record it was imported from; the service (required, its name), the record (required, the URL of the record), the doi, the label the service gives the version (for instance v3 on arXiv), and files: the files kept there that are not in the content (for a deposit, such as a source archive uploaded instead of the sources) or the files received from it (for a source, as they were received before being unpacked), each with name and sha512 (required), md5 and bytes;

  • withdrawal (section 11);

  • extensions: the data of extensions (section 4), an object whose keys are the names of the extensions and whose values are defined by them.

object.json is metadata and is placed under CC0 (section 16).

10. Collections: members.json

10.1 Catalogues and selections

Collections are of two kinds, which differ in how they treat the versions of their members.

  • A catalogue keeps objects whole and is impartial about their versions. Each member pins an object, with all its versions, and the collection may follow it as it grows, whoever adds the versions: the owner of the object decides what its versions are. An archive's main collection (its own documents) and the list of objects an archive mirrors (section 10.4) are catalogues.

  • A selection vets particular revisions: a journal its accepted version, a digest or a review journal the version it reviewed, a reading list the version it recommends. Each member pins a revision set, the document versions the curator vetted; earlier and later versions of the same document are not part of the selection, and the selection changes only by an explicit act of its curator, which is a new version of the selection. A selection may also keep its own copies of the revisions it vetted (section 10.5).

Both kinds may contain collections as members (an archive of archives, a selection of issues). members.json states the kind.

10.2 The member list

A collection version MUST contain members.json with:

  • format: "opensheaf-collection/0.1";

  • type: "catalogue" or "selection";

  • members: a list, in the order in which the members are presented. This order is authoritative: presentations MUST present members in it.

It MAY contain order, the rule by which tools maintaining the collection place members: manual (the default: tools append new members and never reorder), issued-desc or issued-asc (by the members' Issued date, then their Available date, members with neither last, ties broken by object identifier, so that the result is reproducible).

Each member MUST have:

  • kind: document or collection;

  • archive: the archive identifier of the member's archive;

  • archiveUrl: the base URL of that archive when the collection version was made;

  • id: the object identifier.

Each member MAY have mirrors (base URLs of archives holding a mirror of the object, section 10.4), name and owner (its line, section 6.5, so that copies of it can be recognised, and found by name (section 6.6), after its archive disappears), doi (the version DOI), conceptDoi and cite, a cached citation (title, creators as a list of names, year, and issued, the member's Issued date) so that the collection stays readable, and can be ordered, without resolving its members, also if they become unavailable. cite is not authoritative.

Members of a catalogue MUST have version, the pinned object version, and inventorySha512, the SHA-512 digest of that version's inventory file. Since the inventory of an object version lists every earlier version, the pin fixes the object with all its versions up to it. A member MAY have follow, "latest": a curation setting, not a floating reference. A followed member pins the head of the object when the collection version was made; a member without follow keeps the version its curator pinned, which MAY be earlier than the head, until the curator changes it. A tool maintaining the collection reads the member archive's discovery document (or its feed); when the followed object has a new head, the tool writes a new collection version pinning it, whatever the new head holds (a new document version, a description, a notice, a withdrawal): a catalogue does not judge the versions of its members. A withdrawn member stays, and presentations show the withdrawal. Presentations show the current version of each member, read from the history of the pinned version (section 7.3).

Members of a selection MUST have revisions: a non-empty list of the revisions vetted, in the order of the document's history, each with documentVersion, version (the object version vetted, which holds that document version: when several do, the last of them when the revision was vetted, which is its entry in the history, section 7.3) and inventorySha512 (the digest of its inventory file). They MUST NOT have version, inventorySha512 or follow themselves. The revision presented as the selection's is the last of the list. A revision pins the object version that was vetted: descriptions and notices added later by the document's archive are not vetted by the selection, and presentations that show them SHOULD say where they come from; a revision keeps its pin in later versions of the selection. If the document is withdrawn in its archive, the revisions stay vetted, and presentations show the withdrawal as section 11.1 asks, saying that it comes from the member's archive. Tools MUST NOT change revision sets on their own: adding a revision (for instance a corrected version, accepted after review), removing one, or adding or removing a member is a new version of the selection, made by its curator, recorded in the inventory (who and when) with a message saying what was decided. A revision set MAY hold several revisions of the same document, for instance a version accepted and its later correction.

Every member is pinned: a collection version states exactly which object versions it contains, whole objects up to a version in a catalogue, revisions in a selection. A collection version therefore fixes everything it contains, also across archives; since a pin fixes an inventory, which fixes all its files, collections are hash trees. Pins cannot form cycles.

10.3 Members of other archives

A member may belong to another archive. Nothing is copied: the member is resolved as in section 6.4. A reference (a pin without a copy) needs no permission. Copies are of two kinds: mirrors (section 10.4), which are the same line, and branches (section 10.5), which are lines of other owners; accepted copies are shallow branches.

10.4 Mirrors

An archive MAY mirror an object of another archive: copy the whole object, every version with its inventories and files, byte for byte, into its own storage root, under the same identifier (only if no object of its own has it), at the path given by its own layout. A mirror is the same object, not a new one: it also copies the object's witnesses (section 13.2); its object.json files keep naming the original archive, and the discovery document lists it with mirrorOf, the identifier of the original archive (section 6.1). A mirror is brought up to date only by copying the new versions of the original, which is possible because OCFL objects only grow; it MUST NOT be changed otherwise. Mirroring is allowed only if the licences of all the versions copied allow redistribution. A catalogue MAY list a mirror of a member in the member's mirrors. An archive that mirrors another archive entirely SHOULD be listed in the mirrors of that archive's discovery document, with the agreement of its owner.

Mirrors serve preservation and access (an institution keeping copies of its members' archives, an independent storage site): they are impartial, like catalogues, and carry every version.

10.5 Branches and accepted copies

A branch is a line of another owner continuing an object from one of its versions, the branch point: a co-author carrying the work on, a journal keeping the version it vetted and correcting it afterwards. Its genesis record is the object's, so it has the parent's name (section 6.5), or, after a clash, another name of the same genesis record; it copies sealed from its parent. From its first version after the branch point, its object.json records its own owner and parent: the owner, name, archiveId, objectId, objectVersion (the branch point), documentVersion and inventorySha512 of the parent version, and SHOULD record the url of that object version, an absolute URL (<storage root URL><path>/<version>/, with <path> the object's path in the layout of the parent's storage root, section 5), so that it can be resolved (section 6.4). Its datacite.json describes it with the branch owner (for a selection, its archive) as publisher and keeps the relations of the parent version; the first version of a shallow branch, and every version that moves its branch point, SHOULD link the parent version with IsIdenticalTo: its DOI if it has one, otherwise a URL (the url of parent). A branch is deep or shallow.

  • A deep branch holds the parent's object versions up to the branch point, byte for byte, under the parent's object identifier (only if no object of its own archive has it), at the path given by its own layout, and continues them with versions of its own owner. Its common past with the parent is checked by the records of those versions in its inventories, which equal the parent's. It copies every earlier version, so it is allowed only if their licences allow redistribution, or with the agreement of their owners, recorded as agreement in the object.json of its first own version (section 9).

  • A shallow branch holds only the branch point. Its first object version holds exactly the files of the parent version (every file except datacite.json, object.json, parent.inventory.json and parent.object.json, the genesis record included), byte for byte; parent.inventory.json, a copy of the inventory of the parent version; and parent.object.json, a copy of its object.json. Its later versions are its owner's own, and keep genesis.json, parent.inventory.json and parent.object.json unchanged. A shallow branch of a shallow branch names its grandparent through parent.object.json. It needs the right to redistribute only the parent version. This is the evidence #22 proposes for accepted copies.

The evidence of a shallow branch. Its first version shows, without access to the parent, that it is consistent:

  • the name: a name of genesis.json, by the algorithm of its last character;

  • the parent pin: the digest of parent.inventory.json equals inventorySha512 of parent, its id is the parent's objectId and its head the parent's objectVersion;

  • the files: every file of the head state of that inventory, except datacite.json, object.json, parent.inventory.json and parent.object.json, is present at the same logical path with the same digest, no other file is present besides datacite.json, object.json, parent.inventory.json and parent.object.json, and parent.object.json has the digest of object.json in that state;

  • the parent: the fields of parent equal the owner, name, archiveId, objectId and documentVersion of parent.object.json; parent.name is a name of this genesis record, by the algorithm of its last character, and is the branch's own name unless the branch was renamed after a clash (section 6.5), sealed equals that of parent.object.json, the branch's owner differs from the parent's, and the parent's owner is the originator of the genesis record, or parent.object.json declares a parent of its own (the parent is itself a branch);

  • the genesis record: genesis.json is in the head state of that inventory with the same digest.

Consistency is all that these prove: anyone can make a parent inventory that agrees with itself. They do not prove that the parent version is the one its archive keeps. For that a verifier resolves the parent (section 6.4), which confirms the archive that keeps the parent's line, not the person or body its owner names (section 6.6); or, when the parent's owner is keyed, checks its signature of the parent version, which the branch SHOULD keep among its witnesses (section 13.2); or relies on other witnesses (timestamps, external records).

Moving the branch point. A branch MAY take a later version of its parent's line as a new branch point: a journal that vets the authors' corrected version. The new parent has the same owner, name, archiveId and objectId as the previous one, a higher object version, and a document version later than the previous branch point's in the history of the new parent version (its parent.object.json, section 7.3; without history, a higher number), not merely a higher number (a parent version that only changes the description, such as a DOI added, is not a new branch point); a branch point never moves back, and is never dropped. The object version that moves it is the one whose parent differs from the previous version's; it holds exactly the files of the new parent version, as the first version of a shallow branch does, with new copies of parent.inventory.json and parent.object.json, and is checked like that first version (this drops the files of the branch's own notes, such as the files of its notices, which section 7.3 keeps in every later version: how a move keeps them is open, section 6.5), and also for continuity: the new parent inventory continues the previous one when both have the same id, every entry of versions in the previous one is equal, as a JSON value, to the entry of the same version in the new one, and every digest of those entries is in the manifest of the new one. This shows, from the branch alone, that the corrected version continues the version first vetted. A deep branch moves its branch point in the same way; the checks of a deep branch apply to its first branch point only, and for its first move the previous parent inventory is that of its first branch point, vk/inventory.json. The branch stays one sequence of versions under one owner, numbered as section 7.3 says.

Accepted copies. An accepted copy is a shallow branch kept by a selection from a revision it vetted. Its owner is a URI, named or keyed, for the selection or the body behind it (a journal, a review journal), and MUST differ between selections that keep copies of the same document, also in one archive, and MUST NOT be the originator (section 6.5): two selections are two owners, hence two lines. Its later document versions are acts of the selection's curator (a corrected version accepted, a notice, a withdrawal); the authors' later versions change nothing in it. The selection lists the accepted copy as its member, a member of its own archive; it MAY list the original revision set as well. A branch is not a mirror: it is another line, with its own inventories, and its own versions cannot stand for the parent in the resolution of a pin (section 6.4; a deep branch's copied versions, byte for byte the parent's, are copies like any other), so it is never listed in mirrors.

A version that the selection makes itself, such as a journal's typeset version of record, is a later version of the selection's branch, with the selection as publisher, the authors' agreement in object.json (section 9), and relations to the authors' versions (sections 7.3 and 8.1). A branch carries versions of the same work: typesetting, copy-editing, corrections, notices. A derived work (a translation, an abridgement, a commentary or review, a collected edition) is a new object, with its own genesis record and a relation to its source (section 8.1).

Open question: numbering on branches. The branch point keeps its document version (version 3 stays version 3). Later versions of the branch either (a) continue the numbering within the branch (the journal's version 4, distinct from the authors' version 4, the owner telling them apart), or (b) are numbered from the branch point (3.1, 3.2), which reads more clearly but makes documentVersion more than an integer.

10.6 Rights

The member list of a collection is placed under CC0. The licence of a collection never extends to its members. Mirrors and branches keep the licences of what they copy.

11. Withdrawal and takedown

11.1 Withdrawal

A document or collection is withdrawn (for instance retracted by its authors) by a description-only version whose object.json has status withdrawn and a withdrawal object with a date and a reason (a note, section 9), and whose datacite.json has the same date as Withdrawn. The status belongs to the object, whatever document version its head holds. Its content is kept, its history remains verifiable, and the discovery document lists it with status withdrawn. Presentations MUST show the withdrawal notice with the document.

11.2 Takedown

When content must be removed (by law, or for a breach of rights), the object is deleted from the storage root, together with the folders of the hash that the deletion leaves empty (in the hashed layout, section 5, since OCFL forbids empty folders in a storage root), and a tombstone MUST be added to the discovery document.

11.3 Tombstones

A tombstone records id, kind, lastVersion, inventorySha512 of that version, date and reason (plain text, since the discovery document has no content files), and, for an object with a genesis record, its name, ownerId (section 6.6) and sealed, which it MUST record, so that its line stays taken and its genesis record cannot be reused for another work (section 6.5); it MAY also record owner, unless the takedown erases it (section 16). Identifiers of tombstoned objects MUST NOT be reused. Verifiers report a pin to a tombstoned object as "removed", not as a corruption. External copies (DOI records, snapshots) follow the rules of their services.

Note: OCFL 1.1 has no way to remove files from an object short of deleting and rebuilding it. Physical deletion of files, and the flagging of lost or corrupted files, are accepted as in scope for OCFL version 2, with a tombstone or status recorded in the inventory. When that mechanism is published, a later version of this specification will adopt it for takedowns of single files.

12. Versioning of this specification

This specification is versioned MAJOR.MINOR.PATCH, a form of semantic versioning adapted to a format:

  • a major version (1.0, 2.0) may make incompatible changes;

  • a minor version (1.1, 1.2) only adds: every file valid under 1.x remains valid under 1.y for y > x, with the same meaning;

  • a patch version (1.1.1) corrects or clarifies the text without changing any requirement.

Before version 1.0, any change of the minor version (0.1, 0.2, …) may be incompatible, as semantic versioning allows for initial development.

Every JSON file defined here declares its format version, and the discovery document and every object.json declare the version of this specification, both as MAJOR.MINOR only (for instance "opensheaf-object/0.1" and "0.1"): a patch version never changes what is valid, so files do not record it.

A reader that finds a major version it does not know (or, before 1.0, a minor version it does not know) SHOULD report it and MUST NOT silently treat the files as valid. A reader that finds a later minor version of a major version it knows (from 1.0) reads the files as that major version, ignoring properties it does not know, and SHOULD report the version. For this to work, readers MUST ignore unknown properties in files of a major version they know, and the schemas of this specification do not forbid additional properties.

While a version is a draft, successive drafts are identified by the date in the heading and by the changelog (section 17). The text of each version is published at https://opensheaf.org/opensheaf-specification-<MAJOR.MINOR>.md and is not changed after the version is final, except by patch versions, which are listed in its changelog.

13. Integrity and authenticity

13.1 Integrity

Integrity rests on OCFL digests: every file is fixed by its SHA-512 digest in the inventory, every inventory by its checksum file, and every collection version pins its members by inventory digest. Inventories MAY also record MD5 and SHA-256 digests in their fixity block; archives following the Zenodo binding MUST record MD5 (appendix A).

13.2 Authenticity and dates

Digests show that files were not changed; they do not show who made them or when. An archive MAY provide, for each object version:

  • <version>.inventory.json.sha512.sig: a detached signature of the inventory checksum file of that version (<version>/inventory.json.sha512), made with a key listed in keys of the discovery document (each key with a type, such as openpgp or ssh, and a url or fingerprint), or, for a line whose owner is keyed, with the owner's key (below);

  • <version>.inventory.json.sha512.ots: an OpenTimestamps proof of the same file.

These witness files SHOULD be kept in the object's extension folder extensions/opensheaf-witnesses/, so that they travel with the object when it is copied or mirrored. OCFL allows object extension folders, which are not part of any version; the extension name opensheaf-witnesses is not yet registered with OCFL, so validators may warn about it. An archive that does not modify object folders after a version is committed MAY instead keep them under witnesses/<object id>/, next to the discovery document. Witnesses can be added later, by the owner of the line or by others, and replaced when a proof is upgraded (an OpenTimestamps proof is completed once its attestation is confirmed); they are not covered by the inventory digests, and need not be, since each one is checked directly against the checksum file it names, which the pins fix.

The versions of a line whose owner is keyed (section 6.5) MUST carry this signature, made with the owner's key, and its witnesses MUST be kept in the object's extension folder, so that they travel with the object:

  • for a did:key owner, the key MUST be an Ed25519 key, and the signature file holds the 64 bytes of the Ed25519 signature (RFC 8032) of the bytes of the checksum file;

  • for an openpgp4fpr: owner, the signature file is an OpenPGP detached signature (RFC 9580) of the same bytes, and the public key MUST be kept in the extension folder as keys/<fingerprint>.asc, the fingerprint in lowercase hexadecimal.

Witness files are named as follows, all in the extension folder (or, except for keyed lines, under witnesses/<object id>/):

  • <version>.inventory.json.sha512.sig is the signature by the owner of the line to which that object version belongs; in a deep branch, the versions up to the branch point belong to the parent's line, and the branch copies their witnesses with them;

  • keys/<fingerprint>.asc is the OpenPGP public key of an openpgp4fpr: owner;

  • a signature by someone else (a third party vouching for a version) is <version>.inventory.json.sha512.<label>.sig, where <label> is chosen by whoever adds it and matches ^[a-z0-9]+(-[a-z0-9]+)*$, with <version>.inventory.json.sha512.<label>.json, a JSON object with signer (a URI) and, unless signer is a did:key, key (an OpenPGP public key, ASCII-armoured); the signature has the form of an owner's: Ed25519 for a did:key signer, OpenPGP otherwise;

  • a branch keeps the witnesses of each of its branch points in the folder parent/<w>/ (except the first branch point of a deep branch, whose witnesses it copies with the parent's versions, as above), where <w> is its own object version that took that branch point (the first version after it, or the version that moved it): the parent's checksum file <v>.inventory.json.sha512 (where <v> is objectVersion of that parent), checked against parent.inventory.json of <w>; when the parent's owner is keyed, its signature <v>.inventory.json.sha512.sig and, for an OpenPGP key, keys/<fingerprint>.asc; and any other witness of the parent version, named as above (<v>.inventory.json.sha512.ots, <v>.inventory.json.sha512.<label>.sig with its .json).

An OpenPGP signature MAY be made by a signing subkey bound to the key of the fingerprint in the key file kept.

External deposits (appendix A) and software archive snapshots are further witnesses. Archives kept in git MAY also sign their commits or tags, but git hashes are not part of the integrity chain of this specification.

14. Verification

A verifier checking an archive MUST:

  • validate the discovery document, and every object.json (parent.object.json included), members.json and genesis.json, against the schemas of their declared versions (and the index files of section 6.6, if present), checking formats (dates, URIs) as assertions, which JSON Schema 2020-12 leaves optional;

  • validate the storage root and every object against OCFL 1.1 (with a standard OCFL validator or equivalent checks), and check that the storage root's ocfl_layout.json names the layout given by storageLayout, that its configuration does not change the parameters of section 5, and that every object is at the path that layout gives;

  • check that the discovery document lists the objects of the storage root with their kinds, head versions, inventory digests and status as their head versions state them, and that no listed object has the identifier of a tombstone; a verifier reading the archive over HTTP cannot list folders, so it checks the listed objects and reports that completeness was not checked, while a verifier with access to the files also checks that no object is missing;

  • check the requirements of sections 7 to 11 on every object version, including that datacite.json and object.json agree on the document version and on the date of a withdrawal, and that Available, for a version first made public by the archive, is the date of its deposit (section 7.1);

  • check the document versions of each document (section 7.3): object versions with the same document version have the same sources, renditions and change note, except that a version with sourcesMissing may be completed by adding files (section 7.3); new numbers follow the rule of new versions, without gaps (for a branch, from the document version of its first branch point; for a deep branch, its first own version that adds files of the document's own taking the number after the highest document version in the object, last in history; a version that moves the branch point taking the next number, on a deep branch the number after the highest in the object); history, when present, lists distinct document versions, covers all of them, each entry being the last object version holding its document version; no object version after the first one with history lacks it; every notice is kept unchanged in every later object version;

  • check that each members.json has a type, that the members of a catalogue have version and inventorySha512, and that the members of a selection have revisions and none of version, inventorySha512 or follow, with distinct document versions;

  • for the head of each collection, resolve each member (each revision, in a selection) as in section 6.4 and check its pin, and for earlier collection versions check the pins of members of the archive itself (resolving the members of other archives for every earlier collection version is OPTIONAL); for a revision, check that the pinned object version holds the stated document version; for a member with name and owner, check them against the object.json of the pinned version; check that no pin names an object version without a genesis record (section 6.5); report each as verified, mismatch (a copy was found and does not match), unavailable (no copy found) or removed (tombstoned);

  • for each mirror (mirrorOf), check that mirrorOf differs from the archive's own archiveId and that the object.json files of the versions of the mirrored line name that archive (for a mirror of a deep branch, the versions after its branch point; those before name the archive of the line each belongs to); for every other object, that the versions of its line name the archive's own archiveId (for a deep branch, its versions after the branch point; those before are checked as the lines they belong to, each naming the archive and owner of its own line, the parent's or an earlier one's);

  • for each object with a genesis record (section 6.5): that genesis.json is the same in every object version from the first that holds it, that name is its digest by the algorithm named in its last character, that its kind is the kind of object.json, that owner, name, sealed, archiveId and objectId do not change from the first version of the line, that no two objects of the archive (mirrors included), nor an object and a tombstone, have the same name and owner (owner identifier, for a tombstone) at their heads, that objects with the same genesis record have the same sealed, and that an object one of whose names is a tombstone's name has the tombstone's sealed, that a line without parent is named by algorithm 0 and its sealed names its own sealing version, that no two owners at the heads of the archive have the same owner identifier, that owners are written in the forms of section 6.5, that the discovery document lists the head's name and owner, that a line whose owner is not the originator declares a parent and that the originator's line declares none, and, for a keyed owner, the signature of every object version of the line;

  • for each branch (section 10.5): for a deep branch, with first branch point vk, that its own versions hold no parent.inventory.json or parent.object.json until one moves its branch point, that objectVersion of its first parent is vk, that the inventory of vk has the digest inventorySha512 of parent, that owner, name, archiveId, objectId and documentVersion of parent equal those of the object.json of vk, that vk holds the genesis record, and that this parent first appears in v(k+1); for a shallow branch, the evidence of its first version, and that its later versions keep the identity files unchanged until a version that moves the branch point; for every branch, that its owner differs from the owner of parent, that parent.name is a name of its genesis record and its own name unless it was renamed after a clash, that a renamed branch has an algorithm number greater than that of parent.name (a failure otherwise), and that its owner is not the originator; reporting as a warning, not a failure, a rename that neither the objects nor the tombstones of the archive justify, or a number that is not the smallest free one, since the line that caused it may be kept elsewhere; that sealed equals the parent's, and that the parent's owner is the originator of the genesis record or the parent version's object.json (parent.object.json, or, for the first branch point vk of a deep branch, vk/object.json) declares a parent of its own, and declares none when the parent's owner is the originator; for every version that moves the branch point, the same evidence, that the new parent has the same owner, name, archiveId and objectId as the previous one and a higher object version holding a document version later than the previous branch point's in the history of the new parent version, and the continuity of the two parent inventories (section 10.5); for each branch point, report the first of these verdicts that applies: inconsistent (a check fails, or the parent was resolved and does not match), confirmed (the parent was resolved, through a location known independently of the branch (section 6.4), and matches; or, for a keyed parent owner, its signature of the branch point holds), attested (one of these witnesses of the parent version holds: an OpenTimestamps proof of its checksum file, kept in parent/<w>/ (or, for the first branch point of a deep branch, with the copied versions), which proves only that the parent version existed by the date of the proof, reported with that date; a third party's signature with its sidecar, when the verifier's user trusts the signer (a signature by any other key is reported, and leaves the verdict unconfirmed, since the branch's owner can make keys of its own); an external record, such as a DOI deposit, whose files match the parent version, when the verifier's user trusts its depositor or the verifier reached it independently of the branch (others are reported, and leave the verdict unconfirmed); the signature of the branch's own owner does not count), unconfirmed (consistent, with nothing outside the branch); report as the branch's verdict the weakest of those of its branch points (inconsistent, unconfirmed, attested, confirmed, from the weakest); and report separately whether the parent was found, unavailable or removed (tombstoned), and whether it is withdrawn;

  • where several copies of a line are known (mirrors, members, branches' parents), that they agree (section 6.5); two that do not are a fork of the line, reported with the owner's signatures when it is keyed, and with whether each copy is confirmed and by which archive (section 6.6).

A verifier SHOULD check the witnesses it finds, the indexes the archive declares (section 6.6: every entry agrees with the objects and starts with its file's prefix, every object with a genesis record and every sealed version is listed, and tombstoned objects are listed as removed in names/ and sha512/), the requirements of the profiles the archive declares, and those of the extensions it knows; it SHOULD report the extensions it does not know, which do not make an archive fail verification. It MUST NOT treat the presentation as authoritative. It SHOULD limit the depth and size of the collections it follows, and report when it stops.

15. Security considerations

  • Untrusted inventories. Inventories, logical paths and member lists from other archives are untrusted input. Verifiers MUST reject logical paths that break the rules of section 7.1 (absolute, with . or .. segments, not in Unicode normalisation form C), and SHOULD limit the size of the files they fetch.

  • Archives of sources. Tools unpacking source archives (appendix A) MUST guard against paths leaving the target folder and against archives that expand to excessive sizes.

  • Presentation. A website MUST NOT embed HTML of other archives in its own pages; it links to them. Documents' HTML versions are generated by the archive's own tools.

  • Subdomains. A domain that offers subdomains to archives (as opensheaf.org does) MUST remove the DNS records of abandoned archives, to prevent takeover by others.

  • Weak hashes. SHA-1 (as in most git repositories) and MD5 are not used for integrity: MD5 appears only for comparison with external services.

  • Branches and owners (proposal). The evidence a shallow branch carries can be forged consistently: only a resolved parent, a keyed parent owner's signature or other witnesses show that the parent existed. parent.inventory.json and parent.object.json are untrusted input, checked like inventories from other archives. A named owner is only asserted: anyone can write a line under someone's ORCID iD, and only the archive serving it, or keys, distinguish the two. A compromised key lets its holder write forks of a keyed line; rotation and revocation are open (section 6.5, #13).

  • First deposit wins (proposal). An archive refuses a mirror whose line is taken, an object sealed outside it whose line is taken when it is deposited, an object whose genesis record it holds with another sealed, and an owner whose identifier is another owner's (section 6.5), so a forged copy deposited first gets the genuine one refused. A branch whose line is taken is renamed instead: for any object or tombstone in its archive, confirmed or not, and for the owner's confirmed lines elsewhere, never for index entries alone, so forged index entries cannot force renames. A branch point is moved onto an existing branch only under the conditions of section 6.5 (the owner's own branch of the same parent line, a later branch point, in the archive that keeps it), so that a forged branch is never continued as the owner's line; for a named owner, an archive that accepts deposits from more than one depositor binds each named owner URI of the lines it keeps to the depositors it has checked can use it (section 6.5), so that no depositor continues another's genuine line or opens one under another's URI. Archives that accept objects of others (custodians, repositories with many depositors) SHOULD check that a copy is confirmed (section 6.6) before depositing it, and resolve a refusal by checking which copy is (#39).

  • Short forms (proposal). Anyone can publish a line under a named owner's URI whose name starts with a given short form, dated as they like; resolvers therefore order only confirmed lines, reached through the archive that keeps them or signed by the owner's key, and show unconfirmed ones as warnings (section 6.6). Another owner can make a short form ambiguous, but not take it over; files record only complete names, and printed short forms are long enough (16 characters) not to be searched for.

  • Resolving without a digest (proposal). A named owner's line can be forked by anyone, so a copy found through an at hint, an index kept by others or a gateway is only a copy: resolvers and gateways report it as unconfirmed unless it was reached through the archive that keeps the line or is signed by a keyed owner (section 6.6). With no confirmed copy, the latest head among agreeing unconfirmed copies is used, so a party that copies a line and adds versions (a false notice or withdrawal) is shown, marked unconfirmed, until a confirmed copy is found. A gateway that fetches URLs given in links guards against requests to private addresses and against large responses, does not serve archives' files from its own origin, and redirects only, and only temporarily, to confirmed archives, so that a link through it cannot send readers to a location of an attacker's choice.

  • Mutable maps. The discovery document, the indexes and presentation files can be changed by whoever controls the server; their statements are only trusted after checking them against the storage root and the pins.

16. Privacy and rights

  • Documents. Each document carries the licence chosen by its authors in rightsList. "All rights reserved" is allowed: deposit grants readers access, not reuse.

  • Metadata. datacite.json, object.json, members.json, inventories and the discovery document (and, with the proposal of section 6.5, genesis.json, parent.inventory.json, parent.object.json and the index files) are placed under CC0, so that they can be harvested and mirrored freely.

  • Personal data. Archives record only the personal data needed to describe and cite the work (names, identifiers, affiliations) and the depositor of each version. The depositor is recorded in the inventory (section 7.1). Agreement records are minimal (section 9). A request to erase personal data from an immutable history is handled by a takedown (section 11.2); with the proposal of section 6.5, the tombstone and the indexes then keep, of the owner, only the owner identifier (with the name and sealed), not the owner's URI. An owner identifier is a digest of a URI that can often be guessed (an ORCID iD), so it is a pseudonym, not an erasure.

  • Owners (proposal). The originator of a genesis record, and the owner and parent of every version, are copied into every mirror and branch and can never be removed from them. An owner who must stay anonymous, such as the referee of a report (#29), SHOULD be named by a URI that does not identify them, for instance a did:key made for that purpose; the user of the inventory and by of an agreement MUST then not identify them either, since they are copied too.

Appendix A. Zenodo binding (normative for archives declaring the profile zenodo)

Zenodo issues DataCite DOIs (prefix 10.5281) and keeps files permanently. Under this binding:

  • Records. Each document is one Zenodo record with versions: the concept DOI stands for the document, and each document version is one record version with its own DOI, of Zenodo resource type publication-preprint (or the type matching resourceTypeGeneral). Description-only versions are metadata edits of the existing record version, not new record versions; files they add (such as notices) are not uploaded, since the files of a published record version are fixed.

  • Versions out of order. Zenodo orders the versions of a record by publication, and its concept DOI resolves to the latest. A document version deposited out of order (section 7.3) is therefore not deposited as a new version of the record; it MAY be deposited as a separate record, with IsVersionOf the concept DOI of the document.

  • Files. The record version holds the content files of the object version as deposited. Zenodo records have no folders: if the sources have sub-folders, or the record would exceed Zenodo's file count, the sources are uploaded as one archive sources.zip, built reproducibly (entries in byte order of their names, fixed timestamps, no extra attributes), whose digests are recorded in object.json under external, in the entry of the deposit (role deposit). Inventories MUST record MD5 digests in fixity, so that the checksums reported by Zenodo can be compared directly.

  • Order of operations. (1) Create a draft, or a new version of the record (a new version inherits the files of the previous one, which are deleted). (2) Reserve its DOI (Zenodo reserves one with each draft; its sandbox reserves DOIs with the prefix 10.5281 but publishes them with the test prefix 10.5072). (3) Write datacite.json with that DOI and build the object version in a staging area. (4) Upload the files and compare the MD5 checksums reported by Zenodo with the fixity block. (5) Publish. (6) Commit the object version and update the discovery document. If a step fails before publication, the draft is discarded. If publication succeeds and the commit fails, the tool MUST complete the object version from the staging area before any other deposit of that document; it SHOULD hold a lock per document during a deposit, since Zenodo allows one unpublished version per record.

  • Corrections. Zenodo allows the files of a published version to be changed within 30 days. Archives following this binding MUST NOT use this: a correction is a new document version.

  • Metadata differences. Zenodo generates its own DataCite record for the DOI: its url is the Zenodo landing page, its publisher is Zenodo, and it adds relations of its own (such as IsVersionOf the concept DOI). datacite.json remains authoritative; verifiers tolerate exactly these differences.

  • Collections. A collection MAY be deposited when it is explicitly released (not at every change), as a record of type other, with members.json among its files. A Zenodo community MAY group an archive's records for browsing; it is not authoritative.

Appendix B. TeXmacs profile (normative for archives declaring the profile texmacs)

  • The main source is a TeXmacs document; sourceFormat is application/x-texmacs (not a registered media type; it is the type TeXmacs uses).

  • toolchain records the TeXmacs version and the style packages and plugins used that are not part of the TeXmacs distribution; such packages that belong to the document are deposited with the sources.

  • Renditions are produced without regenerating bibliographies or tables of contents, so that the deposited sources, with their stored references, reproduce them even if a bibliography database is not deposited; deposits SHOULD nevertheless include the databases used.

  • The title and abstract in datacite.json are converted from the TeXmacs document to plain text, with mathematics in LaTeX as in section 8.

  • HTML versions are exported by TeXmacs from a copy of the sources with presentation packages added to its style; the deposited sources are not modified.

  • An archive whose files are kept inside a website built with TeXmacs' website converter SHOULD place an empty file .texmacs-noconvert at its top (honoured by the max-html plugin), so that the converter never rewrites deposited files.

Appendix C. Website profile (normative for archives declaring the profile website)

  • Index. The website has an index page generated from the head version of the main collection. It MAY be split into several pages. A flattened, non-authoritative list for programs that do not read OCFL MAY be published as catalog.json.

  • Landing pages. Each document has one landing page, for its current version (section 7.3), with links to every version in the order of the history, each with its external labels, stage, change note and the notices about it, its renditions and sources, its DOI, and the withdrawal notice if any.

  • Search engines. Landing pages MUST carry the meta tags read by Google Scholar: citation_title, citation_author (one per author), citation_publication_date (the Issued date, or else the Available date of the current version), and citation_pdf_url on the same host as the PDF; and SHOULD carry schema.org ScholarlyArticle JSON-LD and FAIR Signposting links (cite-as, describedby, item, license).

  • Feeds. A feed (section 6.1) lists object versions by their created date in the inventory: what is new in the archive.

  • Harvesters. The website SHOULD publish a sitemap.xml, and MAY publish an OAI-PMH static repository file or a ResourceSync description.

  • Citations. Landing pages SHOULD offer BibTeX and CSL-JSON entries generated from datacite.json.

  • Separation. Presentation files are regenerated from the archive and never edited by hand; they do not embed other archives' HTML.

Appendix F. Rationale (non-normative)

  • Why OCFL. It is a published, versioned specification for exactly this problem (versioned objects as plain files with digests), with independent validators, used by research libraries. OpenSheaf adds only discovery and collections.

  • Why the flat-direct layout, and a hashed layout for large archives. Paths stay readable and resolvable by rule over plain HTTP; the cost is short identifiers without /. One folder holding every object becomes impractical at large sizes, mostly in git, where every deposit rewrites a tree listing every object, and in the web views of forges, which show at most about a thousand entries of a folder; object storage, which has no real folders, gains nothing. So a large archive may spread its objects over folders named by the hash of their identifiers (0003-hash-and-id-n-tuple-storage-layout), which keeps the identifier as the name of the object's folder and the path computable by rule (a browser computes SHA-256 natively); an object whose identifier is its name (section 6.5, proposal) is placed in the same way, under the hash of that identifier, which has nothing to do with the digest that made the name; its parameters are fixed so that every client computes the same paths, and the layout is chosen once, since changing it changes every URL into the storage root (though no pin). The layout of Fedora (0004-hashed-n-tuple-storage-layout) was not chosen, since it names the object's folder by the hash alone.

  • Why a discovery document. Static web servers cannot list folders; one small file makes an archive discoverable, and its statements are checked against the storage root.

  • Why pins by inventory digest. One digest fixes a whole object version, so collections become hash trees across archives, and any matching copy will do.

  • Why catalogues and selections. Keeping and vetting are different acts. An archive (an author's, an institution's, a storage site) keeps what its members deposit, every version, without judging them: following an object as it grows is its job. A selection (a journal, a digest, a review journal) vouches for particular revisions: a later version by the authors has not been vetted, so it cannot enter the selection by itself, and a change of what is vetted is an editorial act that the selection's own history records. Pinning whole objects in one case and revision sets in the other makes the difference explicit and checkable.

  • Why mirrors and accepted copies differ. A mirror copies a whole object and stays the same object, owned by its original archive, so it can only grow by the original's versions. An accepted copy takes one vetted revision into the selection's own archive, where it continues under the selection's responsibility (corrections, notices, withdrawal); OCFL cannot hold part of an object, so a copy of one revision is another object: with the proposal of section 6.5, a shallow branch of the same name.

  • Why the owner is part of the identity (proposal). A name alone cannot say whose history is the right one: anyone may copy a genesis record. With (owner, name), copying is no forgery: a copy under another owner is a branch, declared as such, and each owner answers for one line only. Location stays out of the identity, so an object can be kept anywhere.

  • Why deep and shallow branches (proposal). A co-author continuing the work needs its whole past, and can check it by digests; a journal needs only the version it vetted, and may not be allowed to copy the others. A shallow branch carries the parent's inventory and object.json, so that its consistency can be checked after the parent has gone; that the parent version is the one its archive keeps needs the parent, reached through that archive, its owner's signature or other witnesses; that the owner named is the person it claims needs owner proofs (#41).

  • Why separate document and object versions. Readers and DOI services see versions of the work; the storage keeps every change, including corrections of the description.

  • Why the archive numbers document versions itself. External numberings have gaps (versions an external service no longer serves) and do not cover versions that were never public there. The archive's own numbers have no gaps; external labels are recorded beside them.

  • Why an explicit history, and why it lists object versions. Dates may be approximate or unknown, so they cannot order versions, and pointers from each version to the previous one cannot be corrected when a version is inserted later, since earlier versions are fixed. A list kept in each object version, with the head's list authoritative, can be corrected by a new version and keeps a record of what was known before. Its entries name object versions, which are exact and resolved directly through the inventory, and name the last object version of each document version, which carries its most complete description. Digests could not be used: an object version cannot contain the digest of its own inventory.

  • Why the deposit is read from the inventory. OCFL already records when and by whom each object version was made; repeating it in object.json would allow the two to disagree.

  • Why notices are not new document versions. A notice about a version is a later statement about it, not a change of the work. The exact state a reader saw, with or without a notice, is identified by the object version and its pin.

  • Where witnesses live. A witness of an object version can only be made after the version is committed, so it cannot be part of it (a signature of an inventory cannot be listed in that inventory). Putting each signature or timestamp in a new version would mix evidence with changes of the work, and every upgrade of a timestamp proof would be a version. OCFL closes the object folder to anything it does not define, and its logs/ folder is meant for unstructured records of actions and is not covered by digests. Object extension folders are the place OCFL provides for data that is not part of any version (the registered mutable-head extension keeps its data there), so witnesses go in extensions/opensheaf-witnesses/ and travel with the object; witnesses/ outside the storage root remains for archives that never touch object folders after commit.

  • Why no HTML in deposits. Presentations improve; deposits must not change.

  • Why a minimal core, and extensions. The core defines only what every archive and collection needs to be kept, cited, composed and verified. Richer structures among documents (a short account of a proof and its detailed argument, a talk and its paper, a dataset and the analyses built on it, a knowledge base linking results across papers) are built on top of it: by links inside the documents and DataCite relations, which need nothing more, or by extensions that record them with pins, so that tools follow them when they copy, verify or present documents. Keeping them out of the core leaves room for designs not yet imagined, while the pins, which fix extension data with the rest of each version, keep whatever is built checkable.

  • Why DataCite. It is the metadata of DOIs for repositories, with relations for versions, preprints and collections, and it maps directly to Zenodo.
