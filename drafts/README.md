# Working papers

Drafts about OpenSheaf that are not part of the specification: positions,
ideas, comparisons, designs being thought through. They are non-normative.
Where they describe something the specification does not support, they say
so and point to the issue where it is discussed; where they disagree with
the specification, the specification is right.

The papers are plain Markdown, read on GitHub. They are not built into the
site, and they may change or be dropped at any time. A paper that settles
into an agreed design goes into the specification, the FAQ or the use
cases, through an issue.

| Paper | About |
|---|---|
| [positioning.md](positioning.md) | The functions of scholarly communication (record, preserve, announce, filter, distribute, assign merit), OpenSheaf as an exchange layer between the parties that carry them, comparisons with scholarly infrastructure and with federated and distributed systems, what separating the functions costs, and proposals |
| [git-as-implementation.md](git-as-implementation.md) | Git's commits, trees, references and transport as the implementation of OpenSheaf: git instead of OCFL, a deterministic git view of OCFL objects (checkable through Software Heritage), or git as transport only; the lines of PR #30 in git terms; experiments |
| [deployment.md](deployment.md) | Where and how to serve an archive: what a host must do, the hosts that work (static hosting, raw file servers, object storage, institutional web space, WebDAV servers) and those that do not (cloud drives, shared drives, reference managers), the order of uploads, several locations, and how to check a deployment |
| [database.md](database.md) | A database behind an archive: as an index derived from the files, as the storage behind a server that delivers them byte for byte, or instead of them (not recommended); the trap of re-serialising metadata; an index published as a static SQLite file for large archives; Fedora, and why OpenSheaf objects cannot be Fedora objects but Fedora can store and serve an archive's files; experiments |
| [radicle.md](radicle.md) | Radicle, a peer-to-peer network for git repositories, set against OpenSheaf: repositories named by a digest, nodes as identities and peer namespaces as lines, and what the proposal of PR #56 took from them (owners with key logs, archives as hosts, `<owner>/<name>` storage, branches as new objects); seed nodes as mirrors and custodians, signed references and witnesses, collaborative objects; names and RID collisions, read from its source; Radicle as a transport for archives in git, as a model (not recommended), or as a source of designs; its security disclosure of September 2026; experiments |
| [keys-and-forks.md](keys-and-forks.md) | The difficulties met while writing the rules on owners, keys, revocation and forks of PR #30: signatures without time and backdating; old signatures expiring with their keys, and why it failed; retiring and revoking; a signed version confirming what it extends; forks of a key log; unconfirmed and what is mirrored; rules that removed things and became attacks; timestamps as upper bounds, stripping and forks; key logs inside branches; the principles that emerged, the irreducible limit, and how OpenPGP, git, Radicle, TUF, Sigstore and transparency logs meet the same problem |
| [federated-identity.md](federated-identity.md) | How federated and decentralized systems define identity, rotate keys, recover from theft and handle forks (ActivityPub, Matrix, DKIM, Nostr, Scuttlebutt, Hypercore, Keybase, did:plc, CT, Sigstore, key transparency, TUF, Radicle, KERI, Sidetree, DID methods, OpenPGP, ORCID), set against the key-log forks of #58; the lesson that healing needs an order or a commitment made before theft, and a sketch of KERI-style pre-rotation for key logs |
| [matrix.md](matrix.md) | Matrix, the federated messaging standard: how it establishes identity (servers that speak for their users, cross-signing) and shares files (the content repository, authenticated media, encrypted attachments), why it cannot hold an archive or replace owners and keys, and its uses beside an archive: announcing versions, notices with pins, discussion and review, sign-in to services, coordinating a group's signers, first-seen evidence for key logs, files for referees; experiments |
| [alphaxiv.md](alphaxiv.md) | alphaXiv, a service for reading and discussing papers over arXiv that has become a preprint server and an AI reading service, set against OpenSheaf function by function and point by point (fixity, names, versions, withdrawal, rights, preservation, authors, curation, discussion, machine readers); an evaluation of both positions, proposals (grounding AI answers by pins, a resolver for agents, curation as collections), experiments and open questions |
